Don't Ship Skills Without Evals — Philipp Schmid, Google DeepMind

TL;DR

이 영상은 AI 에이전트 개발 시 스킬(skill)의 중요성과 더불어, 배포 전에 반드시 평가(eval)를 거쳐야 하는 이유와 방법을 설명한다. 스킬은 에이전트의 특정 작업을 돕는 도구로, 잘 작성된 스킬은 에이전트 성능을 15%까지 향상시키지만, 비결정론적 특성 때문에 테스트 없이는 효과를 알 수 없다. 영상은 스킬을 잘 작성하고 효과적으로 평가하는 구체적인 8가지 팁과 Google DeepMind의 내부 평가 과정을 공유하며, 항상 스킬을 로드한 경우와 그렇지 않은 경우를 비교하는 '절제 테스트(ablation test)'를 통해 스킬의 유효성을 검증하고 필요 없어진 스킬은 폐기해야 한다고 강조한다.

풀시청 판단

이 영상은 AI 에이전트 개발 및 배포 과정에서 '스킬'의 성능 평가(eval)에 대한 실질적인 지침을 찾는 개발자나 AI 엔지니어에게 특히 유용하다. 스킬이 무엇인지부터 잘 작성하는 방법, 그리고 이를 어떻게 효과적으로 평가하고 관리해야 하는지까지 구체적인 방법론을 제시하므로, 에이전트의 안정성과 효율성을 높이고자 하는 이들에게 강력히 추천한다.

특히 다음 내용을 얻고자 한다면 풀시청할 가치가 있다.

  • 에이전트 스킬의 유형(역량 스킬과 선호 스킬)과 그 관리 전략을 이해하고 싶은 사람.
  • 스킬의 성능을 벤치마크하고 인간이 작성한 스킬과 AI 생성 스킬의 차이를 알고 싶은 사람.
  • 좋은 스킬을 작성하기 위한 [6:37] 8가지 실용적인 팁과 [17:12] 평가(eval) 모범 사례 10가지를 배우고 싶은 사람.
  • Google DeepMind가 내부적으로 스킬 평가를 어떻게 수행하는지 [15:41] 실제 사례를 통해 알아보고 싶은 사람.

영상의 약점은 없으나, 스킬 자체의 구현 방식이나 코드 예시는 거의 다루지 않고, 주로 평가(eval)의 필요성과 전략에 초점을 맞춘다. 따라서 스킬 구현의 기술적 깊이를 기대하는 시청자에게는 다소 표면적일 수 있다.

핵심 내용

에이전트 스킬: 비결정론적 특성 때문에 평가(eval)가 필수다

AI 에이전트가 코드를 작성하거나 생산성 작업을 수행할 때 스킬(skill)을 활용하는 비중은 높지만, 스킬의 성능을 평가하는 체계(evals)를 갖춘 경우는 드물다 [0:39]. SkillBench 벤치마크에 따르면 5만 개 이상의 스킬 중 평가 체계를 갖춘 스킬은 거의 없었다. 대다수 스킬은 AI가 작성했으며 제대로 테스트되지 않았다. 문제는 에이전트가 비결정론적으로 작동하므로, 특정 작업 실패가 스킬 자체의 문제인지, 아니면 모델이 너무 어려운 작업을 수행하려 했기 때문인지 알기 어렵다는 점이다 [1:12]. 따라서 스킬 배포 전 평가는 필수적이다.

직접 쓰는 에이전트와 사용자를 위한 에이전트의 스킬 활용법은 다르다

에이전트 스킬은 두 가지 맥락에서 다르게 사용된다. 첫째는 개발자가 직접 사용하는 에이전트로, 개발자는 스킬의 존재와 작동 방식에 대한 높은 이해도를 바탕으로 에이전트가 특정 스킬을 호출하지 못할 때 즉시 개입하여 프롬프트를 수정하거나 슬래시 명령어를 사용해 스킬을 직접 발동시킨다 [1:40]. 둘째는 고객/소비자를 위해 구축하는 에이전트로, 최종 사용자는 스킬의 존재 자체를 모르며 특정 스킬을 명시적으로 호출하는 프롬프트를 작성하지 않는다. 따라서 이 경우 에이전트는 사용자의 프롬프트 맥락을 기반으로 스킬을 스스로 판단하고 호출해야 한다 [2:01]. 이처럼 사용자 맥락의 차이가 스킬 설계 및 평가 방식에 영향을 미친다.

스킬은 점진적 노출(progressive disclosure) 원칙에 따라 정보를 계층화한다

스킬은 기본적으로 skills.md 파일과 관련 자산으로 구성된 폴더다 [2:31]. 스킬은 점진적 노출(progressive disclosure) 원칙에 따라 정보를 계층화하여 제공한다.

  1. 제목과 설명: 모델이 스킬을 언제 사용해야 할지 알 수 있도록 모델의 컨텍스트에 포함되는 두 문장 내외의 간결한 설명 [2:42]. 이 설명은 모든 모델 호출 시 토큰 비용을 발생시킨다.
  2. 스킬 본문(skills body): 더 자세한 지침과 외부 파일 참조를 포함한다. 모델이 스킬을 사용하기로 결정하면 이 본문이 컨텍스트로 로드된다.
  3. 참조 파일: 가장 깊은 계층으로, 모델이 특정 작업을 해결하기 위해 필요한 모든 맥락 정보를 담고 있다 [3:02]. 예를 들어, AWS와 Google Cloud에 배포하는 스킬이 있다면, 배포 절차 자체는 skills.md에 없어야 하고 각 클라우드별 배포 지침은 별도의 참조 파일로 분리하여 모델이 필요할 때 탐색하도록 한다 [8:37]. 이는 토큰 비용을 절감하고 스킬을 간결하게 유지하는 데 중요하다.

스킬은 임시적인 역량 강화 또는 영구적인 선호 반영을 위해 존재한다

스킬은 크게 두 가지 유형으로 나뉜다 [3:07].

  • 역량 스킬(Capability Skills): 모델이 현재 일관되게 수행하기 어려운 특정 작업을 가르치는 임시적인 스킬이다(예: 로그 추적, React 앱 생성). 모델 성능이 향상되면 이 스킬들은 더 이상 필요 없어져 폐기될 수 있으며, 평가는 언제 스킬을 폐기할 수 있는지 알려준다 [3:25].
  • 선호 스킬(Preference Skills): 특정 팀의 워크플로, 스타일 가이드, 회사 고유의 선호도 등 모델이 자체적으로 학습하기 어려운 고유 지식을 인코딩하는 영구적인 스킬이다. 이는 매우 가치 있으므로 제대로 작동하는지 평가로 보호해야 한다 [3:37].

스킬은 에이전트 성능을 평균 15% 향상시키지만, AI 생성 스킬은 오히려 부정적일 수 있다

SkillBench 1.1 업데이트 분석 결과, 스킬은 개방형 및 폐쇄형 모델 전반에 걸쳐 에이전트 성능을 평균 15% 향상시키는 것으로 나타났다 [4:17]. 그러나 인간이 작성한 스킬이 가장 좋은 성능을 제공하는 반면, AI가 생성한 스킬은 오히려 성능에 부정적인 영향을 미칠 수 있다 [5:11]. 또한, skills.md 파일은 500줄 미만으로 간결하게 유지하는 것이 좋다.

스킬 작성의 8가지 모범 사례

좋은 스킬을 작성하기 위한 8가지 팁은 다음과 같다 [6:37].

  1. 명확한 설명 작성: 모델이 스킬을 언제, 왜, 어떻게 사용해야 할지 명확하게 지시한다.
  2. 명령형 작성: "~해야 한다"는 식의 지시를 명확하게 제시하고, 긴 설명문은 피한다.
  3. 간결하게 유지하고 정보 계층화: 스킬 설명을 짧게 유지하여 토큰 비용을 줄이고, 깊은 정보는 참조 파일로 분리한다.
  4. 적절한 자유도 부여: 모든 단계를 자세히 지시하기보다 모델이 달성해야 할 목표와 제약 조건을 정의한다. 자동화된 스크립트로 처리할 수 있는 고정된 워크플로는 스킬 대신 스크립트를 사용한다 [9:14].
  5. 부정적 사용 사례 포함: 스킬을 언제 사용하지 말아야 하는지에 대한 지침을 제공하여 불필요한 발동을 막는다.
  6. 조기 테스트: 새로운 스킬을 만들 때 긍정적 사용 사례 5개, 부정적 사용 사례 5개 등 10~20개의 프롬프트를 테스트해본다. 실제 사용자 트레이스를 포함하면 더 좋다.
  7. no-ops 제거: AI 생성 스킬에 흔히 나타나는 no-ops(예: "코드를 읽기 쉽게 만들어라")와 같이 에이전트 행동에 실질적인 변화를 주지 않는 지시를 제거하여 토큰 비용을 절감한다 [11:12].
  8. 스킬 폐기 시점 알기: 모델이 스킬 없이도 동일한 성능을 달성하면 해당 스킬은 폐기하여 비용과 유지보수 부담을 줄인다. 절제 테스트로 이를 확인할 수 있다.

Google DeepMind의 스킬 평가: JSON 테스트 케이스와 정규 표현식/LLM 검사

Google DeepMind는 Gemini Interactions API 스킬 개발 시 117개의 테스트 케이스를 만들었다 [13:03]. 실제 사용자 데이터와 합성 데이터, 피드백을 기반으로 한 이 테스트로 유효한 코드 생성 성능을 90%까지 향상시켰다. 이 평가는 두 가지 간단한 자산을 사용한다 [13:38].

  1. JSON 테스트 케이스 파일: 프롬프트, 언어(TypeScript, Python), 스킬 발동 여부(should trigger), 그리고 예상되는 검사(expected checks)를 포함한다.
  2. Python 스크립트: 코딩 에이전트(예: Gemini CLI)를 실행하고 출력을 파싱하여 예상 검사 결과를 확인한다.

대부분의 스킬 평가는 정규 표현식(regex) 기반으로 수행한다 [14:38]. 예를 들어, 올바른 SDK, 모델, 메서드를 사용하는지, 오래된 패턴이 없는지 등을 확인하는 간단한 검사들을 저렴하게 실행한다. 더 복잡한 스킬의 경우 LLM as a judge 방식을 사용하여 에이전트가 수행한 전체 단계나 트레이스를 평가할 수 있다 [15:16].

모든 스킬 변경은 반드시 평가를 거치고 회귀 테스트로 성능 저하를 막는다

Google DeepMind는 내부적으로 모든 스킬 옆에 평가(evals)를 함께 배치한다 [15:53]. 각 테스트는 프롬프트, 격리된 작업 공간(환경), 시작 명령, 그리고 정규 표현식 기반 스크립트나 LLM as a judge를 통한 검사를 포함한다. 스킬 파일에 변경(diff)이 발생하면 반드시 평가가 실행되며, 테스트 케이스의 성능을 향상시키지 않는 변경은 병합되지 않는다 [16:42]. 이는 회귀 테스트(regression test) 역할을 하여 스킬 변경으로 인한 성능 저하를 방지한다.

주요 통찰·논점

'스킬 설명'은 에이전트의 작동 비용이자 핵심 효율성 지표다

스킬 설명은 에이전트가 스킬을 호출할지 결정하는 핵심 요소이며 [6:51], 모든 모델 호출 시 컨텍스트에 포함되어 토큰 비용을 발생시킨다 [7:57]. 따라서 설명이 너무 약하면 스킬이 너무 자주 발동되거나, 너무 강하면 필요한 시점에 발동되지 않을 수 있다. 또한, 설명이 길면 불필요한 토큰 비용이 계속 발생한다. 즉, 스킬 설명은 에이전트의 스킬 발동 정확성과 운영 비용에 직접적인 영향을 미치므로, 간결하고 명확하게 작성하고 엄격하게 평가해야 한다 [17:24].

에이전트의 비결정성 때문에 여러 차례의 격리된 절제 테스트가 필수다

에이전트와 모델은 비결정론적이므로 [19:02], 한 번의 테스트로 스킬의 효과를 확신할 수 없다. 따라서 평가 시에는 여러 번의 시도(multiple trials)를 수행하여 신뢰성을 측정해야 한다 [19:09]. 또한, 에이전트는 기존 환경의 이전 대화나 실행 기록을 참조하여 "부정행위"를 할 수 있으므로 [18:42], 반드시 격리된(isolated) 환경에서 테스트해야 스킬 자체의 순수한 효과를 정확히 측정할 수 있다. 마지막으로 절제 테스트(ablation test)를 통해 스킬을 로드했을 때와 로드하지 않았을 때의 성능을 비교해야 스킬의 실제 기여도를 파악하고, 필요 없어진 스킬을 폐기할 시점을 알 수 있다 [21:11].

no-ops 제거와 부정적 테스트는 비용 절감과 안정성을 위한 핵심 요소다

no-ops(예: "코드를 읽기 쉽게 작성하세요")는 에이전트의 행동을 바꾸지 않으면서 불필요한 토큰 비용을 발생시킨다 [11:17]. 이러한 no-ops를 제거하면 비용을 절감할 수 있다 [20:50]. 또한, 스킬이 언제 발동되어야 하는지에 대한 긍정적 테스트만큼이나 스킬이 언제 발동되지 말아야 하는지에 대한 부정적 테스트(negative tests)는 중요하다 [9:56]. 부정적 테스트는 스킬이 불필요하게 과도하게 발동되는 것을 막아 에이전트의 효율성을 높이고 혼동을 줄인다. 이 두 가지는 에이전트 시스템의 비용 효율성과 안정성을 동시에 높이는 실용적인 방법이다.

  • "코딩 에이전트는 '부정행위'를 잘한다" [18:42]는 표현은 격리된 테스트 환경의 중요성을 직관적으로 보여준다. 에이전트가 외부 맥락(이전 대화, 실행 기록)을 통해 스킬을 사용하지 않고도 '답을 훔쳐볼' 수 있다는 점을 상기시킨다.
