TL;DR

이 강의는 대규모 언어 모델(LLM)을 구축하는 데 필요한 핵심 구성 요소를 개괄적으로 설명한다. 특히 사전 훈련, 사후 훈련, 데이터, 평가, 시스템 측면에 초점을 맞추며, LLM의 성능 향상에 연산량과 데이터 규모가 결정적인 역할을 한다는 스케일링 법칙을 강조한다. 또한 LLM을 AI 비서로 정렬(alignment)하는 사후 훈련 방법인 지도 미세 조정(SFT)과 인간 피드백 기반 강화 학습(RLHF), 그리고 RLHF의 간소화된 버전인 직접 선호 최적화(DPO)에 대해서도 설명한다.

풀시청 판단

이 강의는 대규모 언어 모델(LLM)의 기본 원리부터 실제 구축에 필요한 주요 단계와 과제를 폭넓게 다루는 밀도 높은 자료이다. 특히 아키텍처나 훈련 알고리즘의 세부 사항보다는 데이터 처리, 평가, 시스템 최적화, 그리고 LLM을 실제 애플리케이션에 적합하게 만드는 사후 훈련(alignment) 과정에 관심 있는 사람에게 매우 유용하다.

다음과 같은 사람에게 풀시청을 권한다.

  • LLM의 훈련 및 배포 과정 전반에 대한 깊이 있는 이해를 얻고자 하는 머신러닝 엔지니어, 데이터 과학자, 연구자.
  • LLM 개발에서 데이터의 중요성과 그 처리 과정의 복잡성을 이해하고 싶은 사람.
  • LLM의 성능을 예측하고 최적의 자원 할당 방법을 고민하는 사람(스케일링 법칙).
  • ChatGPT와 같은 AI 비서가 어떻게 개발되는지, 특히 인간 피드백이 어떻게 활용되는지 궁금한 사람.
  • ML 시스템 최적화, 특히 GPU 활용 및 연산 효율성 향상 기법에 대해 알고 싶은 사람.

일부만 시청해도 충분한 경우:

  • LLM의 사전 훈련 과정에 집중하고 싶다면, 토큰화, 평가, 데이터, 스케일링 법칙 및 비용 관련 내용이 포함된 "[3:34] 사전 훈련: 언어 모델링의 핵심 원리"부터 "[54:05] 비터 레슨: 스케일과 단순함의 가치"까지 시청한다.
  • LLM의 사후 훈련 및 정렬(alignment) 기법에 관심 있다면, "[59:56] 사후 훈련: LLM을 AI 비서로 정렬하기"부터 끝까지 시청한다.

약점 및 한계:

  • 강의는 LLM 아키텍처(예: 트랜스포머)의 세부 사항을 다루지 않는다. 이는 이미 별도의 강의나 온라인 자료가 많다는 이유에서다. 따라서 아키텍처에 대한 기초 지식이 없으면 일부 내용 이해에 어려움을 겪을 수 있다.
  • LLM 시스템 최적화 부분은 시간이 부족하여 간략하게 다루어진다. GPU 활용률, 병렬화, MoE(전문가 혼합)와 같은 중요한 시스템 개념들이 충분히 설명되지 못한다.
  • LLM 개발에 대한 학계와 산업계의 관점 차이를 언급하지만, 산업계의 실제 비공개 정보(예: 데이터 수집의 구체적인 방법, 비용에 대한 정확한 추정)는 제한적으로만 다뤄진다.

핵심 내용

LLM 훈련의 다섯 가지 핵심 구성 요소

대규모 언어 모델(LLM)을 훈련하는 데 필요한 다섯 가지 핵심 구성 요소는 아키텍처, 훈련 손실 및 알고리즘, 데이터, 평가, 그리고 시스템이다 [1:02]. 강연자는 대부분의 학계 연구가 아키텍처와 훈련 알고리즘에 집중하지만, 실제 산업계에서는 데이터, 평가, 시스템이 훨씬 더 중요하다고 강조한다 [2:17]. 이 강의에서는 주로 아키텍처를 제외한 나머지 네 가지 구성 요소를 심층적으로 다룬다.

사전 훈련: 언어 모델링의 핵심 원리

사전 훈련(pretraining)은 LLM이 인터넷상의 방대한 텍스트 데이터를 학습하여 일반적인 언어 패턴과 지식을 습득하는 과정이다 [3:06]. LLM은 기본적으로 토큰 시퀀스(단어 또는 하위 단어)의 확률 분포를 모델링하며, 특정 문장이 인간에 의해 생성되거나 온라인에 나타날 확률을 예측한다 [3:47]. 예를 들어, "The mouse ate the cheese"와 같이 문법적, 의미적으로 올바른 문장에는 높은 확률을, 오류가 있는 문장에는 낮은 확률을 할당한다 [4:04]. 현재 주로 사용되는 자기회귀 언어 모델(autoregressive language model)은 이전 토큰들을 기반으로 다음 토큰을 예측하는 방식으로 작동하며 [5:15], 이때 교차 엔트로피 손실(cross-entropy loss)을 최소화하여 텍스트의 로그 우도(log likelihood)를 최대화한다 [9:37].

토크나이저: LLM 입력의 숨겨진 복잡성

토크나이저(tokenizer)는 LLM이 텍스트를 처리할 수 있는 작은 단위(토큰)로 분할하는 역할을 한다 [10:50]. 단순히 단어 단위로 분할하면 오타나 비라틴어 언어(예: 태국어) 처리, 그리고 새로운 단어 출현에 문제가 발생한다 [11:01]. 반대로 문자 단위로 분할하면 시퀀스 길이가 너무 길어져 트랜스포머 모델의 연산 복잡도(길이에 비례하여 제곱으로 증가)를 감당하기 어렵다 [11:45]. 이러한 문제들을 해결하기 위해 토크나이저는 일반적으로 3~4개의 글자로 구성된 공통 부분 시퀀스를 하나의 토큰으로 묶는다. 바이트 쌍 부호화(BPE)는 가장 흔히 사용되는 토크나이저 훈련 알고리즘 중 하나로, 텍스트 코퍼스에서 가장 빈번한 문자 쌍을 새로운 토큰으로 병합하는 과정을 반복하여 어휘 집합을 구축한다 [12:32]. 토크나이저가 입력 텍스트를 어떻게 분할하는지는 LLM의 성능에 큰 영향을 미치며, 특히 수학 연산이나 코드를 이해하는 데 중요한 역할을 한다 [18:03].

LLM 평가: 퍼플렉시티에서 벤치마크까지

LLM의 성능을 평가하는 전통적인 방법은 퍼플렉시티(perplexity)이다 [19:13]. 퍼플렉시티는 모델이 다음 토큰을 예측할 때 주저하는 정도를 나타내며, 1에 가까울수록 모델의 예측이 완벽함을 의미한다 [20:28]. 그러나 퍼플렉시티는 사용된 토크나이저와 데이터셋에 따라 달라지기 때문에 학계 벤치마킹에서는 더 이상 널리 사용되지 않는다 [21:06]. 대신 학계에서는 MMLU(Massive Multitask Language Understanding)와 같은 표준 자연어 처리(NLP) 벤치마크를 활용하여 LLM의 광범위한 지식과 추론 능력을 평가한다 [22:00]. 이러한 벤치마크는 주로 객관식 질의응답 형태로, 모델이 올바른 답변을 생성할 우도를 평가하거나 가장 적합한 보기를 선택하도록 유도한다 [23:35]. 평가의 주요 과제로는 평가 방식의 불일치와 훈련 데이터에 테스트 데이터가 포함되는 훈련-테스트 오염(train-test contamination) 문제가 있다 [26:05].

LLM 데이터: 방대한 인터넷에서 고품질 정보 추출

LLM 훈련 데이터는 '인터넷 전체'를 사용한다고 하지만, 실제로는 웹 크롤러(예: Common Crawl)로 수집된 2,500억 페이지에 달하는 1페타바이트 이상의 데이터를 정제하는 복잡한 과정이 필요하다 [29:19]. 이 과정은 HTML에서 텍스트 추출, 유해 콘텐츠(예: PII, NSFW) 필터링, 상용구(boilerplate) 및 중복 내용 제거, 낮은 품질의 문서(예: 너무 짧거나 긴 문서) 필터링, 그리고 위키피디아 참조를 통한 고품질 데이터 선별 등을 포함한다 [30:48]. 필터링된 데이터는 도메인(예: 코드, 책, 엔터테인먼트)별로 분류되어 훈련에 대한 가중치가 조절될 수 있으며, 훈련 마지막 단계에서는 위키피디아와 같은 매우 고품질의 데이터를 사용하여 모델을 미세 조정하기도 한다 [34:37]. 현재 최고의 LLM은 약 15조 개의 토큰으로 훈련되며, 이는 초기 벤치마크 모델보다 약 100배 더 많은 양이다 [40:11]. 데이터 수집 및 정제는 LLM 개발에서 핵심적인 부분이며, 효율적인 처리, 도메인 균형, 합성 데이터 생성, 멀티모달 데이터 활용 등 많은 연구 과제가 남아 있다 [37:59].

스케일링 법칙: 성능 예측과 자원 최적화

2020년경부터 발견된 스케일링 법칙(scaling laws)은 LLM이 더 많은 데이터로 훈련되고, 더 많은 매개변수를 가질수록 성능(테스트 손실)이 항상 향상된다는 것을 보여준다 [41:07]. 이는 일반적인 머신러닝에서 나타나는 과적합(overfitting) 현상과는 달리, 모델 크기나 데이터 양을 늘리면 손실이 로그 스케일에서 선형적으로 감소하는 경향을 보인다 [41:20]. 이 법칙 덕분에 연구자들은 제한된 연산 자원 내에서 모델 크기와 데이터 양을 어떻게 배분할지 최적화할 수 있다 [44:57]. 예를 들어, Chinchilla 연구는 최적의 훈련 자원 할당을 위해 매개변수 하나당 약 20개의 토큰을 사용하는 것이 가장 낮은 손실을 얻을 수 있음을 발견했다 [51:35]. 그러나 추론 비용까지 고려하면 더 작은 모델이 선호될 수 있어, 매개변수 하나당 150개의 토큰 비율이 실제 운영되는 모델에 더 적합하다고 제안된다 [52:17].

LLM 훈련 비용: 수천만 달러와 탄소 발자국

LLM 훈련에는 막대한 비용과 자원이 소요된다. 예를 들어, Meta의 Llama 3 400B 모델은 15.6조 토큰으로 훈련되었고, 4,050억 개의 매개변수를 가진다 [55:26]. 이는 약 3.8e25 FLOPs의 연산량을 필요로 하며, 16,000개의 H100 GPU를 사용하여 약 70일(2,600만 GPU 시간)이 걸렸을 것으로 추정된다 [57:02]. 이를 임대 비용으로 환산하면 약 5,200만 달러에 달하며, 개발 인력의 급여를 포함하면 총 7,500만 달러 이상의 비용이 들었을 것으로 예상된다 [58:13]. 또한 이 과정에서 약 4,000톤의 CO2 상당량의 탄소가 배출되는데, 이는 JFK-런던 왕복 항공권 2,000매와 맞먹는 수준이다 [58:35].

사후 훈련: LLM을 AI 비서로 정렬하기

사후 훈련(post-training)은 사전 훈련된 LLM을 사용자의 지시를 따르고 특정 의도(예: 유해한 콘텐츠 회피)에 부합하는 AI 비서로 만드는 정렬(alignment) 과정이다 [59:56]. 사전 훈련된 모델은 인터넷 텍스트의 패턴을 모방하여 질문 다음에 또 다른 질문을 생성하는 경향이 있는데 [1:00:12], 이는 AI 비서가 원하는 방식이 아니다. 사후 훈련은 크게 지도 미세 조정(SFT)과 인간 피드백 기반 강화 학습(RLHF)으로 나뉜다. 이 과정을 통해 LLM은 단순히 언어 모델링을 넘어 사용자의 의도를 이해하고 유용하며 안전한 답변을 생성하도록 학습된다.

지도 미세 조정(SFT): 인간 데이터로 모델 방향 잡기

지도 미세 조정(SFT)은 사전 훈련된 LLM을 인간이 직접 생성한 이상적인 질문-답변 쌍 데이터셋으로 미세 조정하는 과정이다 [1:02:24]. 이 과정에서 모델은 다음 토큰 예측이라는 언어 모델링 작업을 수행하지만, 인간이 원하는 형식과 내용에 더 집중하게 된다 [1:02:37]. SFT는 GPT-3가 ChatGPT로 발전하는 데 핵심적인 역할을 했지만 [1:03:31], 인간 데이터 수집이 느리고 비싸다는 문제가 있다 [1:03:51]. 이를 해결하기 위해 Alpaca 프로젝트처럼 LLM을 사용하여 추가적인 질문-답변 데이터를 생성하는 합성 데이터 생성(synthetic data generation) 방식이 도입되었다 [1:04:03]. 흥미로운 점은 SFT에 필요한 데이터의 양이 생각보다 많지 않다는 것이다 [1:05:31]. 이는 SFT가 모델에 새로운 지식을 가르치기보다는, 사전 훈련된 모델이 이미 알고 있는 다양한 답변 방식 중 특정 사용자 유형(AI 비서)에 최적화되도록 유도하기 때문으로 해석된다.

인간 피드백 기반 강화 학습(RLHF): 인간 선호도 최대화

SFT는 인간의 생성 능력에 한계가 있고, 모델이 새로운 지식을 학습하지 못해 환각(hallucination)을 유발할 수 있으며 [1:10:05], 이상적인 답변을 생성하는 데 비용이 많이 든다는 문제가 있다 [1:11:16]. 이러한 한계를 극복하기 위해 인간 피드백 기반 강화 학습(RLHF)이 도입된다. RLHF는 인간의 행동을 단순히 복제하는 대신, 인간의 선호도를 최대화하는 것을 목표로 한다 [1:12:30]. 이 과정에서 모델은 여러 답변을 생성하고, 인간 평가자가 이 중 선호하는 답변을 선택한다 [1:13:01]. 인간의 선호도를 이진 보상(binary reward) 대신 연속적인 값으로 반영하기 위해 별도의 보상 모델(reward model)을 훈련시키는 경우가 많다 [1:14:10]. 이 보상 모델은 인간이 선호하는 답변에 높은 점수를 부여하도록 학습되며, 이 점수를 기반으로 근접 정책 최적화(PPO)와 같은 강화 학습 알고리즘을 사용하여 LLM을 미세 조정한다 [1:16:50]. RLHF는 ChatGPT의 성공에 결정적인 역할을 했지만 [1:18:23], 강화 학습의 복잡성으로 인해 구현이 매우 어렵다는 단점이 있다 [1:18:55].

직접 선호 최적화(DPO): RLHF의 간소화된 대안

근접 정책 최적화(PPO) 기반 RLHF의 복잡성을 해결하기 위해 스탠포드에서 직접 선호 최적화(DPO)라는 새로운 방법론이 제안되었다 [1:19:41]. DPO는 보상 모델 훈련과 강화 학습 단계를 건너뛰고, 인간의 선호도 데이터를 사용하여 LLM의 우도(likelihood)를 직접 최적화한다 [1:19:56]. 즉, 인간이 선호하는 답변의 생성 확률을 높이고 선호하지 않는 답변의 생성 확률을 낮추는 방식으로 모델을 훈련한다 [1:20:02]. DPO는 수학적으로 PPO와 동등한 전역 최솟값을 가질 수 있으며 [1:20:51], 구현이 훨씬 간단하면서도 PPO와 유사한 성능을 달성하여 오픈 소스 및 산업계에서 표준 방식으로 자리 잡고 있다 [1:22:39].

사후 훈련 데이터 수집의 난제와 LLM 활용

RLHF 데이터를 인간이 직접 수집하는 것은 느리고 비싸며 [1:23:43], 평가 지침이 복잡하여 인간 평가자들 간의 일관성도 낮다(약 66% 일치) [1:26:30]. 또한 인간은 내용의 정확성보다 형식(예: 길이)에 치중하는 경향이 있어, RLHF 모델이 불필요하게 긴 답변을 생성하는 원인이 되기도 한다 [1:24:42]. 이러한 문제를 해결하기 위해 LLM을 인간 평가자 대신 사용하여 RLHF 데이터를 수집하는 방법이 도입되었다 [1:25:46]. LLM은 인간보다 훨씬 저렴하고 빠르게 데이터를 생성할 수 있으며 [1:26:56], 인간 평가자들 간의 일치도보다 높은 일치도를 보이기도 한다 [1:27:01]. 이는 LLM이 분산이 적기 때문이다. 현재는 인간과 LLM을 함께 활용하여 RLHF 데이터 수집의 효율성과 품질을 높이는 방향으로 나아가고 있다.

사후 훈련 LLM 평가: 인간과 LLM 평가자의 조합

ChatGPT와 같이 사후 훈련된 LLM은 개방형 질문에 대한 답변을 생성하므로, 단순한 검증 손실이나 퍼플렉시티로는 평가하기 어렵다 [1:28:00]. 이러한 모델은 특정 분포를 모델링하기보다는 정책을 최적화하도록 훈련되었기 때문에 우도 기반의 평가 지표는 적합하지 않다 [1:29:13]. 따라서 실제 사용자 질문에 대한 여러 모델의 답변을 인간 평가자가 비교하고 선호도를 매기는 방식이 주로 사용된다 [1:29:56]. ChatBotArena가 대표적인 예시로, 수십만 명의 무작위 사용자가 두 개의 챗봇과 익명으로 대화하며 더 나은 답변을 선택하게 하여 모델 순위를 매긴다 [1:30:10]. 하지만 이 방법은 비용과 시간이 많이 들고, 평가자의 기술적 배경에 따라 질문 분포가 편향될 수 있다는 단점이 있다 [1:30:52]. 이를 보완하기 위해 LLM을 평가자로 활용하는 AlpacaEval과 같은 벤치마크가 개발되었는데 [1:31:10], 이는 ChatBotArena와 98%의 높은 상관관계를 보이면서도 훨씬 저렴하고 빠르게 평가를 수행할 수 있다 [1:31:53]. 그러나 LLM 평가자는 긴 답변을 선호하는 등 특정 편향을 가질 수 있어, 길이와 같은 요인을 제어하기 위한 회귀 분석 등의 보정 기법이 필요하다 [1:32:11].

LLM 시스템 최적화: 저정밀도 연산과 연산자 융합

LLM 훈련에서 연산량은 가장 큰 병목 현상이며, GPU의 부족과 GPU 간 통신 지연으로 인해 단순히 더 많은 GPU를 구매하는 것만으로는 해결하기 어렵다 [1:37:14]. GPU는 높은 처리량(throughput)과 병렬화에 최적화되어 빠른 행렬 곱셈에 강점을 가지지만 [1:38:00], 연산 속도에 비해 메모리 및 통신 속도가 느리다는 문제가 있다 [1:38:46]. 이는 GPU의 활용률(model FLOP utilization)이 낮아지는 원인이 된다 [1:39:31]. 이러한 문제를 해결하기 위한 시스템 최적화 기법 중 하나는 저정밀도(low precision) 연산이다 [1:40:04]. 32비트 부동 소수점 대신 16비트 부동 소수점을 사용하여 통신량을 줄이고 메모리 소비를 낮춰 연산을 가속화한다 [1:40:43]. 일반적으로 모델의 가중치는 32비트로 저장하고, 실제 연산은 16비트로 수행한 후 다시 32비트로 업데이트하는 자동 혼합 정밀도(automatic mixed precision) 방식을 사용한다 [1:40:51]. 또 다른 중요한 기법은 **연산자 융합(operator fusion)**이다 [1:42:28]. 이는 GPU의 전역 메모리와 연산 프로세서 간의 데이터 이동이 느리다는 점을 이용한다. 여러 연산(예: x.cosine(), x1.cosine())을 개별적으로 실행하면 매번 데이터를 전송해야 하지만, 이들을 하나의 "융합 커널(fused kernel)"로 묶어 한 번만 데이터를 전송하고 모든 연산을 수행한 후 결과를 다시 전송하여 통신 오버헤드를 크게 줄인다 [1:42:31]. PyTorch의 torch.compile 기능이 이러한 연산자 융합을 자동으로 수행하여 모델 속도를 최대 2배까지 향상시킬 수 있다 [1:42:46].

주요 통찰·논점

'더 크고 더 많은' 법칙: 스케일링이 지배하는 LLM 개발

이 강의의 핵심 통찰 중 하나는 LLM 개발을 지배하는 '스케일링 법칙'이다 [41:07]. 매개변수 수를 늘리거나 훈련 데이터를 늘리면 모델 성능(테스트 손실)이 예측 가능하게 향상된다는 점은 기존 머신러닝의 과적합 개념을 뒤엎는 놀라운 결과였다 [41:15]. 이는 LLM 개발에서 아키텍처의 미세한 개선보다는 컴퓨팅 자원과 데이터의 양적 투입이 훨씬 중요하다는 '비터 레슨(쓰라린 교훈)'을 뒷받침한다 [54:05]. 따라서 LLM 개발의 핵심은 최적의 자원 배분(매개변수 대 토큰 비율)과 효율적인 시스템 최적화를 통해 주어진 연산 자원을 최대한 활용하는 것이다.

데이터 품질과 정렬이 LLM의 '지능'을 결정한다

LLM의 '지능'과 활용성은 단순히 방대한 데이터로 사전 훈련하는 것을 넘어, **데이터의 품질과 모델의 '정렬'**에 의해 결정된다 [37:59]. 인터넷은 '더러운' 데이터로 가득 차 있으며, 이를 체계적으로 정제하고 필터링하는 데이터 엔지니어링 과정이 LLM의 성능에 지대한 영향을 미친다. 또한, 사전 훈련된 모델이 단순히 언어를 모방하는 것을 넘어, 인간의 의도를 이해하고 유용하며 안전한 답변을 생성하도록 '정렬'시키는 사후 훈련 과정(SFT, RLHF, DPO)이 ChatGPT와 같은 AI 비서의 성공을 이끌었다 [59:56]. 이 과정에서 인간 피드백은 필수적이지만, 그 비용과 난이도 때문에 LLM을 평가자로 활용하는 혁신적인 접근법이 등장했다.

LLM 개발은 학계와 산업계의 협업 및 관점 차이가 중요

강의 전반에 걸쳐 학계와 산업계의 연구 초점과 동기가 다르다는 점이 여러 차례 강조된다 [2:17]. 학계는 새로운 아키텍처나 훈련 알고리즘 개발에 집중하는 경향이 있지만, 산업계는 데이터 관리, 효율적인 평가, 그리고 실제 시스템 배포 및 최적화에 더 큰 가치를 둔다. 또한 데이터 수집의 법적 문제(저작권)와 경쟁 우위 확보를 위한 기업들의 정보 비공개 전략도 언급된다 [38:28]. LLM 기술의 발전은 이러한 학계와 산업계의 노력이 상호작용하면서 이루어지고 있으며, 때로는 오픈 소스 커뮤니티의 기여(예: Alpaca, AlpacaEval, DPO)가 산업계의 혁신을 촉진하기도 한다 [1:04:03].

인상적인 지점

  • GPT-3와 ChatGPT의 차이: 사전 훈련된 GPT-3가 "달 착륙을 6살 아이에게 설명해달라"는 질문에 "중력 이론을 6살 아이에게 설명해달라"는 다른 질문을 이어 붙이는 식으로 답변하는 반면 [1:00:12], ChatGPT는 적절한 답변을 생성하는 예시는 사전 훈련된 모델과 사후 훈련된 AI 비서 간의 근본적인 차이를 명확하게 보여준다. 이는 사후 훈련, 즉 '정렬'이 LLM의 실제 유용성에 얼마나 결정적인지를 직관적으로 설명한다.
  • LLM 평가의 '인간성': ChatGPT와 같은 모델의 개방형 답변을 평가할 때, 가장 신뢰할 수 있는 방법이 수십만 명의 무작위 사용자가 직접 답변을 비교하고 선호도를 매기는 ChatBotArena라는 점이 인상적이다 [1:30:10]. 이는 기술이 발전해도 결국 '인간적인' 기준이 최종적인 가치를 결정한다는 점을 시사한다.
  • 시스템 최적화의 '보이지 않는 마법': x.cosine()과 같은 간단한 파이토치(PyTorch) 코드 한 줄이 내부적으로는 GPU 메모리-연산기 간의 비효율적인 데이터 왕복을 수없이 일으킨다는 설명 [1:41:40]은 시스템 최적화가 단순한 성능 향상을 넘어 하드웨어의 물리적 한계를 극복하는 '마법'에 가깝다는 인상을 준다. torch.compile과 같은 기능이 이러한 복잡성을 개발자로부터 숨긴 채 2배의 속도 향상을 가져온다는 점이 놀랍다 [1:42:46].
