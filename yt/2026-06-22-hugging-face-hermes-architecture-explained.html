TL;DR

이 영상은 Hermes AI 에이전트의 핵심 아키텍처를 심층적으로 설명한다. 에이전트의 동작 주기, 대화 맥락 생성 방식, 메시징 서비스 연결을 위한 게이트웨이, 그리고 장기 기억 및 정기 작업을 처리하는 크론 잡 시스템을 다룬다. 사용자가 직접 에이전트를 만들거나 Hermes를 효율적으로 활용하는 데 필요한 기술적 이해를 제공한다.

풀시청 판단

Hermes AI 에이전트의 내부 작동 방식에 관심 있는 개발자나 AI 에이전트 구축을 고려하는 사람에게 특히 유용하다. 에이전트의 각 구성 요소(에이전트 루프, 맥락 구축, 게이트웨이, 메모리, 크론 잡)가 어떻게 상호작용하는지 명확하게 이해할 수 있다.

  • 배울 점:

    • Hermes 에이전트가 사용자 메시지에 반응하고 학습하며 응답하는 전체 루프.
    • soul.md, user.md, memory.md와 같은 핵심 파일이 에이전트의 성격과 학습에 어떻게 기여하는지.
    • 대규모 언어 모델(LLM)의 컨텍스트 창 한계를 관리하기 위한 맥락 압축(context compression) 기법.
    • 다양한 메시징 플랫폼(Telegram, Slack 등)을 통해 에이전트와 통신하게 해주는 게이트웨이의 역할과 작동 방식.
    • 내부(SQLite) 및 외부 메모리 시스템이 에이전트의 장기 기억과 학습 능력을 어떻게 확장하는지.
    • 정해진 시간에 특정 작업을 자동으로 수행하는 크론 잡(cron job)의 구현과 활용.

  • 약점 및 한계:

    • 일부 내용은 Hermes 에이전트를 직접 설치하고 설정하는 과정에 대한 사전 지식을 전제로 한다.
    • 외부 메모리 시스템에 대한 설명은 각 공급자별 세부 구현 방식까지는 깊게 다루지 않고 간략히 소개하는 수준에 머문다.
    • 코드를 직접 보여주는 부분이 많지 않아, 비개발자에게는 일부 기술적 설명이 다소 추상적으로 느껴질 수 있다.

핵심 내용

Hermes 에이전트의 전체적인 구성 요소

Hermes 에이전트 아키텍처는 몇 가지 핵심 구성 요소로 이루어진다. 사용자 인터페이스는 CLI, API, 그리고 Telegram, 이메일, Slack 등 다양한 메시징 서비스에 연결하는 게이트웨이로 나뉜다 [1:21]. 에이전트의 핵심은 AI 에이전트 코어로, 자체적인 에이전틱 루프를 통해 작동한다. 이 코어는 사전 설치된 도구(tools)와 스킬(skills)을 활용하며, 내부 및 외부 메모리 시스템과 연결되어 있다. 내부 메모리는 대화 기록을 저장하고, 외부 메모리는 MemZero 같은 외부 공급자를 활용할 수 있다 [2:14]. 이 외에도 에이전트의 성격과 사용자 정보를 정의하는 soul.md 및 user.md와 같은 파일이 중요하다.

Hermes 에이전트 루프: 대화와 학습의 순환

Hermes 에이전트의 작동 방식은 매우 간단한 루프를 따른다. 이 루프는 사용자가 메시지를 보낼 때마다 실행된다.

  1. 사용자 메시지 전송: 사용자가 에이전트에게 메시지를 보낸다 [4:27].
  2. 맥락(Context) 구축: Hermes는 메시지를 받으면 내부 메모리(soul.md, user.md, memory.md, 대화 기록 등)와 사전 정의된 프롬프트를 바탕으로 현재 대화의 맥락을 구축한다 [4:41].
  3. LLM으로 전송: 구축된 전체 맥락과 메시지 기록이 대규모 언어 모델(LLM)로 전송된다 [4:56].
  4. 도구(Tool) 호출 및 실행: LLM은 필요에 따라 웹 검색, 파일 읽기/쓰기 등의 도구를 호출할 수 있다. 도구 실행 결과는 다시 LLM으로 전달되며, LLM이 더 이상 도구 사용이 필요 없다고 판단할 때까지 이 과정이 반복된다 [6:03].
  5. 최종 응답: 모든 도구 호출이 끝나면 LLM은 사용자에게 최종 응답을 제공한다 [6:34].
  6. 메모리 업데이트: 최종 응답 후 에이전트는 메시지를 분석하여 기억할 만한 가치가 있는 내용을 메모리에 저장한다. 이 과정을 통해 Hermes는 지속적으로 학습하고 개선된다 [6:48].

Hermes의 맥락(Context) 구축: 에이전트의 개성과 지식

Hermes의 맥락은 에이전트가 대화에서 참조하는 모든 정보를 의미하며, 주로 마크다운 파일과 대화 기록으로 구성된다 [8:10].

  • soul.md: 에이전트의 성격, 영감, 목표, 어조 등을 정의하는 파일이다 [8:21]. 처음 설치 시 비어 있지만, 사용자가 직접 작성하거나 Hermes가 스스로 작성하도록 지시하여 에이전트를 맞춤 설정할 수 있다.
  • user.md: 에이전트가 사용자로부터 학습한 정보를 저장하는 파일이다 [9:58]. 예를 들어, 사용자가 자신의 직업이나 관심사에 대해 말하면 에이전트가 이를 자동으로 기록한다.
  • memory.md: 사용자에 대한 정보 외의 일반적인 사실, 도구 사용법, 워크플로, 대화 중 학습한 흥미로운 내용 등 임의의 기억을 저장하는 파일이다 [10:38]. 이 파일은 에이전트가 미래 대화에 유용하다고 판단할 때 업데이트된다.
  • 과거 대화 요약: 외부 메모리가 설정된 경우, 현재 대화와 관련성이 높은 과거 대화 요약이 맥락에 포함된다 [12:04].
  • 스킬 및 도구 설명: 에이전트가 사용할 수 있는 스킬과 도구에 대한 설명도 맥락에 포함된다 [12:41].
  • 메시지 기록: 최근 대화 메시지 전체 또는 일정 기준을 초과할 경우 요약된 메시지 기록이 맥락의 가장 중요한 부분으로 포함된다 [12:47].

맥락 압축: LLM 컨텍스트 창 관리

LLM의 컨텍스트 창(context window)은 처리할 수 있는 토큰 수에 한계가 있다. Hermes는 이 한계를 극복하기 위해 맥락 압축 기능을 사용한다.

  • 압축 트리거: 기본적으로 전체 컨텍스트 창의 50%가 사용되면 맥락 압축이 트리거된다. 이 비율은 사용자 설정에 따라 70%나 80% 등으로 변경할 수 있다 [14:21].
  • 압축 시점: 압축은 두 가지 시점에 확인된다. 첫째, 각 대화 턴(turn) 전(LLM 호출 전)에 맥락 크기를 확인한다. 둘째, LLM이 컨텍스트 창 오류를 반환할 경우 즉시 압축을 수행한다 [15:30].
  • 토큰 수 측정: 첫 메시지 전에는 총 문자 수를 4로 나누어 대략적인 토큰 수를 추정한다. 첫 메시지 이후에는 LLM 제공자가 반환하는 실제 사용량(usage response) 데이터를 통해 더 정확한 토큰 수를 측정한다 [16:51].
  • 압축 프롬프트: Hermes는 압축을 위해 상세한 시스템 프롬프트를 사용하여 LLM에 대화 요약을 요청한다. 이 프롬프트는 전체 목표, 제약 사항, 완료된 작업, 현재 상태, 진행 상황, 막힌 부분, 주요 결정, 해결된 질문, 관련 파일 등 다양한 섹션으로 요약을 구성하도록 지시한다. 이는 다른 미니멀리스트 에이전트보다 훨씬 풍부한 맥락 요약을 생성한다 [18:35].

게이트웨이: 다양한 메시징 서비스와 에이전트 연결

Hermes 게이트웨이는 사용자가 Telegram, WhatsApp, 이메일, Slack 등 다양한 메시징 플랫폼을 통해 에이전트와 소통할 수 있도록 하는 시스템이다 [20:24].

  • 작동 방식: 게이트웨이는 async IO 루프를 시작하여 구성된 다양한 메시징 서비스로부터 들어오는 메시지를 지속적으로 수신하고 폴링한다 [21:49]. 각 서비스(웹훅, 소켓, API 폴링 등)마다 메시지를 수신하는 방식이 다르기 때문에, 각 게이트웨이 통합은 개별적으로 설정해야 한다.
  • 맥락 재구성: 게이트웨이는 단순히 메시지를 수신하는 것을 넘어, 들어온 단일 메시지로부터 전체 대화 맥락과 기록을 재구성하는 중요한 역할을 한다 [24:03]. 메시지 기록은 각 게이트웨이(예: Telegram)의 세션 ID를 식별자로 사용하여 로컬 SQLite 데이터베이스에 저장되며, 새로운 메시지가 오면 과거 기록을 쿼리하여 에이전트에게 보낼 전체 맥락을 생성한다 [25:23].
  • 세션 관리자: 게이트웨이에는 세션 관리자가 포함되어 있어, 사용자가 빠르게 여러 메시지를 보낼 경우 에이전트의 현재 작업을 중단(interrupt)시킬지, 지시(steer)할지, 아니면 대기열(queue)에 넣을지를 결정한다. 이는 /interrupt, /steer와 같은 특정 명령어를 통해 제어할 수 있다 [26:48].

Hermes의 다층적 메모리 시스템

Hermes는 에이전트가 장기적으로 학습하고 과거 정보를 기억할 수 있도록 세 가지 주요 메모리 방식을 사용한다.

  1. 마크다운 파일:
    • soul.md: 에이전트의 성격과 목표를 정의한다 [28:54].
    • user.md: 에이전트가 사용자로부터 학습한 개인 정보를 저장한다 [28:59].
    • memory.md: 에이전트가 대화에서 얻은 일반적인 지식과 유용한 사실을 저장한다 [28:55]. 이 파일들은 시스템 프롬프트 바로 뒤에 컨텍스트에 추가되어 LLM이 참조하도록 한다.
  2. SQLite 데이터베이스: 모든 세션의 전체 대화 기록을 저장한다 [29:34]. 이는 게이트웨이가 과거 메시지 기록을 재구성할 때 활용되며, 유사성 검색을 쉽게 할 수 있도록 텍스트만 모아둔 테이블도 포함한다.
  3. 외부 메모리: MemZero, Super Memory, Honcho 등 전문화된 외부 메모리 공급자를 활용할 수 있다 [31:22]. 이 기능은 기본으로 활성화되어 있지 않지만, 에이전트의 학습 능력을 크게 향상할 수 있다. 외부 메모리는 대화의 첫 메시지 이후, 에이전트가 사용자의 의도를 파악한 다음 쿼리되어 다음에 나올 질문에 대비하거나 관련 과거 정보를 불러온다. 마치 사람이 질문에 답하면서 동시에 과거 관련 대화를 떠올리는 방식과 유사하다 [33:32].

크론 잡(Cron Jobs): 에이전트의 자동화된 정기 작업

Hermes의 크론 잡은 에이전트가 특정 시간에 반복적으로 작업을 수행하도록 자동화하는 기능이다 [34:53]. 서버의 크론 프로세스와는 독립적으로 Hermes 내에서 자체적인 루프로 작동하며, 매분 tick 함수를 실행하여 예약된 작업을 확인한다 [35:24].

  • 활용 예시: 매일 아침 AI 관련 최신 뉴스를 이메일로 보내거나, 매주 금요일 상사에게 업무 보고 이메일을 보내는 등의 작업을 설정할 수 있다 [35:52].
  • 저장 방식: 문서에는 SQLite에 저장된다고 되어 있으나, 실제로는 .Hermes/cron/jobs.JSON 파일에 JSON 형태로 저장된다는 점이 흥미롭다 [36:50]. 에이전트는 이 JSON 파일을 매분 확인하여 실행할 작업이 있는지 판단한다.
  • 결과 저장: 실행된 각 크론 잡의 결과는 .Hermes/cron/output 디렉토리 내의 해당 작업 ID별 마크다운 파일에 저장된다 [38:00].
  • 알림 전달: 크론 잡이 생성하는 알림은 에이전트가 직접 "메시지 보내기" 도구를 호출하는 것이 아니라, 사용자가 게이트웨이를 설정할 때 지정한 "홈 메시징 플랫폼"으로 시스템이 자동으로 전달한다 [39:04].

주요 통찰·논점

모듈성과 심플함 속에서 복잡한 에이전트 기능 구현

Hermes 아키텍처는 에이전트 코어, 게이트웨이, 메모리, 크론 잡 등 비교적 간단하고 모듈화된 구성 요소들로 이루어져 있다. 그러나 각 구성 요소가 유기적으로 연결되어 LLM의 한계를 보완하고, 지속적인 학습, 다양한 플랫폼 연동, 자동화된 작업 수행 등 고도화된 에이전트 기능을 구현한다. 특히 맥락 구축과 압축, 다층적인 메모리 시스템은 단순한 LLM 호출을 넘어 지능적인 대화와 학습을 가능하게 하는 핵심적인 설계이다.

장기 기억과 학습을 위한 다단계 메모리 전략

Hermes는 단기적인 대화 기록부터 장기적인 학습 및 지식 관리를 위해 soul.md, user.md, memory.md와 같은 내부 마크다운 파일, 전체 대화 기록을 위한 SQLite 데이터베이스, 그리고 보다 정교한 지능형 메모리 관리를 위한 외부 메모리 공급자를 조합하여 사용한다. 이 다단계 접근 방식은 에이전트가 단순히 현재 대화에 반응하는 것을 넘어, 사용자의 성격과 습관을 학습하고, 과거 경험을 통해 더 나은 결정을 내리며, 광범위한 지식을 활용하도록 돕는 중요한 통찰이다.

게이트웨이를 통한 LLM 에이전트의 접근성 확장

게이트웨이 시스템은 Hermes 에이전트가 CLI나 API를 넘어 Telegram, Slack, 이메일 등 다양한 일상적인 메시징 플랫폼에서 접근 가능하게 하는 핵심 요소다. 이는 에이전트가 더 넓은 사용자 기반과 상호작용하고 실제 세계에 통합될 수 있도록 하는 중요한 디자인 선택이다. 특히, 게이트웨이가 단순히 메시지를 전달하는 것을 넘어 각 플랫폼의 특성을 고려하여 대화 맥락을 재구성하고 세션을 관리하는 복잡한 역할을 수행한다는 점은, 다중 플랫폼 통합의 실제 난이도와 해결책을 보여준다.

인상적인 지점

  • 크론 잡 저장 방식에 대한 솔직한 고백: 발표자가 문서에는 크론 잡이 SQLite에 저장된다고 되어 있지만, 자신의 분석으로는 JSON 파일에 저장되는 것을 확인했다고 솔직하게 밝히는 부분이 인상적이다 [36:50]. 이는 기술 문서와 실제 구현의 차이를 명확히 짚어주어 신뢰를 높인다.
  • 외부 메모리 쿼리 방식의 인간적 비유: 외부 메모리가 첫 메시지 응답 후에 쿼리되어 다음 질문에 대비하는 방식이 마치 "사람이 질문에 답하면서 동시에 과거 관련 대화를 떠올리는 방식과 유사하다"고 비유하는 설명은, 복잡한 메커니즘을 직관적으로 이해시키는 데 큰 도움을 준다 [33:32].
  • 맥락 압축 프롬프트의 상세함: Hermes의 맥락 압축 프롬프트가 목표, 제약 사항, 진행 상황, 결정, 질문, 파일 등 십여 가지 세부 항목을 포함하여 요약하도록 지시하는 것은, 단순 요약을 넘어 에이전트가 스스로 중요한 정보를 파악하고 관리하도록 돕는 정교한 설계임을 보여준다 [19:01].
