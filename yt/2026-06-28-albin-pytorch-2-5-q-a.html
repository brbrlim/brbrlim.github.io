핵심 내용

PyTorch 2.5의 주요 특징

PyTorch 2.5는 대규모 언어 모델(LLM) 환경의 성능 최적화, 컴파일러(torch.compile) 개선, 그리고 다양한 플랫폼 지원에 중점을 둔다 [1:02].

가장 중요한 특징으로는 Flex Attention, SDPA(Scaled Dot Product Attention)의 새로운 백엔드 등 LLM 관련 성능 개선이 있다 [1:37]. 이는 기존 모델의 효율적인 구동을 돕고, 새로운 실험을 위한 유연성을 제공한다. 또한 torch.compile의 compile_autograd 및 영역별 컴파일(regional compilation)과 같은 기능이 추가되어 컴파일 시간을 단축하고 성능을 향상하며 더 많은 사용 사례를 지원한다 [2:06]. 마지막으로, 컴파일러 백엔드인 Inductor의 Windows 지원과 장치 확장의 자동 로딩을 통해 더 많은 플랫폼에서 PyTorch를 쉽게 사용할 수 있게 된다 [2:42].

Python GIL 제거의 영향과 PyTorch의 대응

Python 3.13에서는 GIL(Global Interpreter Lock) 제거 옵션이 도입되어, 스레딩 효율을 크게 높일 수 있게 됐다 [3:48]. GIL은 Python에서 스레드 안전성을 보장하지만, CPython에서 스레드 활용을 제한하는 시스템이다. Python 3.13은 일반 버전과 no-GIL 버전 두 가지로 출시됐다.

현재 PyTorch는 소스 빌드 및 나이틀리 바이너리에서 이 no-GIL 버전을 지원하지만, 광범위한 테스트는 아직 완료되지 않은 상태다 [4:46]. PyTorch 팀은 스레드 안전성 강화를 위해 내부적으로 많은 수정 작업을 진행했으며, 2.5.1 또는 2.6 버전에서는 완전히 테스트를 마친 no-GIL 바이너리를 제공할 계획이다 [5:33]. 사용자가 나이틀리 빌드를 통해 문제를 발견하면 GitHub에 보고해 줄 것을 요청한다.

Triton의 역할과 다양한 가속기 지원

Triton은 다양한 하드웨어(NVIDIA GPU, AMD GPU, Intel XPU, CPU)를 위한 효율적인 커널(kernel) 작성을 지원하는 중요한 프로젝트다 [5:55]. PyTorch는 Triton을 기본적으로 지원하며, 특히 컴파일러 스택인 Inductor가 Triton을 적극적으로 활용하여 여러 백엔드를 지원한다.

CUDA 외의 가속기 지원과 관련하여, eager 모드에서는 필요한 모든 확장 지점(extension point)을 제공하여 사용자가 자체 장치 및 백엔드를 정의하고, 자동 로딩 기능을 통해 PyTorch 코어 백엔드와 유사한 경험을 얻을 수 있다 [8:11]. 컴파일러 스택 측면에서는 하드웨어 특성과 기존 컴파일러 스택의 상태에 따라 통합 방식이 달라진다. Triton은 GPU와 유사한 새로운 시스템에 적합하며, XLA나 Hali와 같은 백엔드는 컴파일러 스택의 다른 지점에 통합될 수 있다 [9:23]. PyTorch 팀은 개발자 포럼을 통해 새로운 장치 통합에 대한 논의와 지원을 환영한다.

혼합형 데이터 임베딩 및 멀티모달 모델

혼합형 데이터(예: 테이블형 데이터와 텍스트)를 위한 임베딩 생성은 점점 중요해지는 추세다. PyTorch는 torch.multimodal과 같은 새로운 라이브러리 및 에코시스템 도구를 통해 이러한 멀티모달 사용 사례를 지원한다 [12:13]. PyTorch 코어는 필요한 저수준 빌딩 블록을 제공하며, 상위 레벨의 복합적인 작업은 전문화된 패키지들을 활용하도록 권장한다.

화자는 가장 중요한 모범 사례로 데이터의 균일화(uniformizing data)를 꼽는다 [13:07]. 데이터를 가능한 한 균일하게 만들면 GPU가 더 효율적으로 연산할 수 있고, 결과적으로 더 나은 모델 성능을 얻을 수 있다. 아무리 좋은 아이디어를 바탕으로 한 희소한(sparse) 데이터라도, 효율적인 연산이 뒷받침되지 않으면 충분한 성능을 내기 어렵다고 강조한다.

torchtext 단종 및 대체 솔루션

torchtext 라이브러리는 현재 단종(discontinued)되었다 [19:04]. 이는 LLM 시대의 변화하는 요구사항과 PyTorch 생태계 내에서의 역할 변화 때문이다. torchtext의 기능은 이제 다양한 다른 라이브러리에서 더 잘 제공된다.

주요 대체 솔루션은 다음과 같다:

  • PyTorch 코어 유틸리티: torchtext의 기본 계층, 데이터 로딩 유틸리티 등은 이제 PyTorch 코어에 직접 포함되어 있다 [20:13].
  • Hugging Face Transformers: LLM 및 트랜스포머 관련 특화 유틸리티를 위한 가장 인기 있는 대안이다 [20:59].
  • torch.tune 및 기타 라이브러리: 파인튜닝, 추론 등의 엔드투엔드 워크플로우를 위해서는 torch.tune, Lightning, Hugging Face의 전문화된 라이브러리가 더 나은 사용자 경험을 제공한다 [21:24].
  • torch.media 등 멀티미디어 시스템: 텍스트를 넘어 멀티미디어 데이터를 다루기 위한 라이브러리가 등장하고 있다 [22:05].

주요 통찰·논점

eager 모드와 torch.compile의 조화로운 미래

PyTorch는 eager 모드의 동적 특성과 유연성을 유지하면서 torch.compile을 통해 성능을 극대화하는 균형점을 찾고 있다 [23:00]. 화자는 torch.compile의 목표를 "사용자가 아무런 생각 없이 코드를 작성해도 최적 성능의 80%를 얻을 수 있도록 하는 것"으로 설명한다 [25:01].

과거 eager 모드에서는 개발자가 수동으로 연산 중첩(overlap compute)이나 인라인화(inline)와 같은 복잡한 트릭을 사용하여 성능을 최적화해야 했다. 이는 파이썬답지 않은 코드를 작성하게 만들었다. torch.compile은 이러한 간극을 메워 가장 자연스러운 코드로도 높은 성능을 얻게 한다. 남은 20%의 성능은 그래프 끊김(graph break) 제거, 컴파일러 힌트 제공 등 추가적인 노력을 통해 점진적으로 개선할 수 있다 [26:22]. 결국 eager 모드와 torch.compile은 모두 중요한 역할을 하며, 유연성과 성능 사이의 부드러운 전환을 제공하는 것이 PyTorch의 목표다.

SDPA 백엔드 변경과 수치 정확성/훈련 발산 문제

cuDNN 백엔드를 SDPA에 도입하면서 일부 사용자가 훈련 발산(training divergence) 문제를 겪고 있다는 질문이 제기됐다 [34:40]. PyTorch는 릴리스 간 또는 CUDA 버전 변경 시 부동 소수점(floating point) 연산의 비트 단위 동일성을 보장할 수 없다. 이는 사소한 초기 오차가 증폭되어 모델의 행동에 큰 영향을 미칠 수 있음을 의미한다 [16:11].

cuDNN 백엔드의 변경은 출력 레이아웃(output layout)과 스트라이드(stride)를 변화시키고 [37:30], 이는 다운스트림 레이어(downstream layers)의 입력과 역전파 경로(backward path)의 grad_output에 영향을 미친다. 결과적으로 서로 다른 알고리즘 구현이 호출되어 미묘한 수치적 부정확성(numerical inaccuracies)이 발생할 수 있다. 특히, 무작위적인(unstructured) 오차는 훈련에 큰 영향을 주지 않지만, 편향된(biased) 또는 구조화된(structured) 오차는 훈련 발산을 유발할 수 있다 [36:46]. 이러한 문제를 해결하기 위해서는 사용자가 문제를 재현할 수 있는 최소 예시를 제공하는 것이 가장 중요하다고 강조한다.

공식 릴리스 vs. 나이틀리 빌드 vs. 소스 빌드

PyTorch 사용자들은 안정성, 최신 기능 접근성, 특정 종속성 요구사항에 따라 세 가지 버전 중 하나를 선택할 수 있다 [42:41].

  • 공식 릴리스(예: 2.5.0): 안정성을 최우선으로 하며, torch.nn, optim, autograd, 기본 분산 시스템과 같이 오랫동안 사용되어온 안정적인 코어 구성 요소를 주로 사용할 때 적합하다 [44:15].
  • 나이틀리 빌드(nightly builds): 최신 기능(torch.compile 패스, 컴파일러 성능 개선, 최신 분산 기능, 텐서 서브클래스 등)을 사용하고 버그 수정이 중요한 경우에 추천된다 [44:28]. 나이틀리 빌드는 모든 CI(Continuous Integration) 테스트가 통과될 때만 제공되므로 상대적으로 안정성이 높다 [50:28].
  • 소스 빌드(build from source): 특정 종속성 버전(예: 오래된 CUDA 버전), C++ 라이브러리 통합, 특정 cuDNN 버전 등 맞춤형 환경이 필요할 때 사용한다 [45:40]. 소스 빌드는 공식 릴리스 스냅샷 또는 나이틀리 브랜치 중 하나를 기반으로 할 수 있다. 대부분의 사용자에게는 사전 패키지된 바이너리 사용이 더 간단하다.

LibTorch (C++ 백엔드)의 미래

LibTorch는 PyTorch의 C++ 백엔드로, 두 가지 주요 역할을 한다 [51:13].

첫째, 순수 C++ 딥러닝 프레임워크로서 torch.nn, 옵티마이저(optimizer), autograd 등 파이썬 PyTorch의 모든 기능을 C++로 제공한다 [51:47]. 이 부분은 사용자층이 제한적이고 유지보수가 어려워 현재로서는 큰 개발 계획이 없다.

둘째, C++를 통해 PyTorch를 확장하려는 개발자를 위한 기능이다 [52:19]. 이 부분은 매우 활발하게 투자되고 있다.

  • Python + C++ 혼합 개발: PyTorch는 Python과 C++를 혼합하여 사용하는 방향으로 발전하고 있다 [53:38]. 고급 컴파일러 스택(TorchScript에서 export/AOT로 변화), 새로운 커스텀 op API, C++ 패키징 등을 통해 파이썬으로 작성된 모델도 C++에 버금가는 성능을 낼 수 있다 [54:51].
  • C++ 추론 환경: 훈련 시에는 Python 오버헤드가 크지 않으므로 Python을 사용하길 권장하지만 [55:56], 대규모 추론 환경에서는 마지막 몇 퍼센트의 성능 향상이나 Python GC(가비지 컬렉터)와 같은 요소로 인한 예측 불가능성을 제거하기 위해 C++ 추론 시스템을 제공한다. 이는 모바일, 엣지 장치와 같이 엄격한 런타임 제약이 있는 환경(예: execute_torch)에 특히 유용하다 [57:21].
  • 유연성 vs. 성능: C++ 환경으로 내려갈수록 더 높은 성능과 예측 가능성을 얻지만, 파이썬의 유연성을 희생해야 한다 [57:51]. 개발자는 훈련 및 실험 단계에서는 파이썬을 사용하고, 모델이 최종적으로 확정되어 프로덕션에 투입될 때 C++ 환경으로 전환하는 유연한 접근 방식을 취할 수 있다.

인상적인 지점

  • eager 모드와 torch.compile의 관계를 설명하며, "파이썬으로 자연스럽게 코드를 작성해도 최적 성능의 80%를 얻고, 추가적인 노력으로 100%에 도달하는 부드러운 전환"이라는 비유는 PyTorch의 개발 철학을 매우 명확하게 보여준다 [25:01]. 이는 유연성과 성능이라는 두 마리 토끼를 잡으려는 PyTorch의 노력을 잘 드러낸다.
