[한글자막] 사람이 아닌 에이전트를 위한 문서 작성법: OpenWiki 내부 공개

TL;DR

이 영상은 AI 에이전트만을 위한 코드 저장소 문서화 도구인 OpenWiki를 소개한다. OpenWiki는 에이전트가 코드를 효율적으로 이해하고 변경하도록 돕기 위해 설계되었으며, 자동 생성 및 유지보수 기능을 제공한다. 초기에는 에이전트 전용으로 구상했으나, 실제 사용에서는 사람 개발자도 함께 문서를 활용하려 한다는 점을 깨닫고 사용자 경험을 개선했다.

풀시청 판단

이 영상은 AI 에이전트의 작동 방식, 특히 기억(memory) 구현에 관심 있는 개발자나, 코드 저장소 문서화의 비효율성을 개선하려는 팀에 유용하다. OpenWiki의 핵심 가치는 에이전트가 코드를 더 효율적으로 이해하고 상호작용하게 하는 것에 있다. 에이전트가 코드를 직접 작성하는 비중이 늘어나는 환경에서, 에이전트의 효율성을 높이는 문서화 방식에 대한 고민과 해결책을 구체적으로 제시한다.

영상의 장점은 OpenWiki의 설계 철학과 기술적 구현 방식을 명확하게 설명한다는 점이다. 특히 에이전트 전용 문서가 기존 사람 중심 문서와 어떻게 달라야 하는지, 그리고 Google의 Open Knowledge Format (OKF)을 활용하여 에이전트의 검색 및 필터링 효율을 높이는 방안은 흥미로운 통찰을 제공한다. 초기 개발 과정에서 발견한 사람 사용자의 필요성과 그에 따른 변경점도 중요한 교훈이다.

단점은 초기 평가 결과가 아직 매우 초기 단계이며, 더 구체적인 벤치마크 데이터를 추가로 공개할 예정이라고 밝히는 점이다 [9:50]. 현재는 Deep Sweet 벤치마크의 일부 작업에서 효율성 향상(토큰 소모 감소)과 소폭의 성공률 증가를 보였지만, 더 광범위하고 엄격한 평가 결과는 아직 공개되지 않았다. 또한, 에이전트가 코드를 직접 작성하는 비중이 아직 크지 않은 조직에게는 당장 적용하기에 설득력이 부족할 수도 있다.

  • ### 에이전트 전용 문서의 특성: 조각 단위 검색과 컨텍스트 창 최적화
  • ### OpenWiki가 만드는 문서의 구조와 핵심 요소: OKF와 문서 간 연결
  • ### OpenWiki의 효과: 에이전트 효율성 증대와 토큰 소모 감소
  • ### 초기 예상 오류: 사람 또한 에이전트 문서를 읽고 싶어 한다
  • ### OpenWiki CLI의 작동 방식: 초기 설정(init)과 자동 업데이트(update)

핵심 내용

에이전트의 차세대 핵심 — 범용 기억(general-purpose memory)

발표자는 AI 분야의 다음 큰 흐름을 범용 기억(general-purpose memory)으로 본다 [0:50]. 지난 몇 년간 에이전트 연구의 중요한 영역이었지만, 아직 범용적인 방식으로 잘 구현된 사례가 없다고 판단한다. OpenWiki는 이 문제를 해결하기 위해 코드 저장소 문서를 시작점으로 삼았다 [1:11]. 이는 잘 정의된 영역이면서도 어떤 코드 기반에도 적용할 수 있는 범용 기억 해결책을 구축하기에 적합하다고 보았다. 최신 LLM과 에이전트 아키텍처 덕분에 이제 이러한 시스템 구축이 가능해졌다는 생각이다.

OpenWiki의 세 가지 핵심 원칙: 에이전트 우선, 쉬운 설치, 자동 업데이트

OpenWiki는 세 가지 핵심 원칙을 기반으로 설계되었다.

  1. 에이전트 전용 문서 작성 [1:31]: 기존 많은 문서 시스템은 에이전트와 사람 모두를 대상으로 하지만, 이는 문서의 구조와 내용을 결정하는 데 있어 절충을 필요하게 한다. OpenWiki는 에이전트가 코드 작성의 많은 부분을 담당하므로, 문서 또한 에이전트가 소비하기에 최적화되어야 한다고 주장한다.
  2. 쉬운 설정 [2:04]: 개발자 도구인 만큼, 설정이 매우 쉬워야 한다. NPM을 통해 단일 명령어로 설치하고, open wiki init 명령어로 API 키 설정, 모델 선택, 위키 지침 정의 등 온보딩 과정을 간결하게 안내한다 [4:13].
  3. 자동 업데이트 [2:18]: 문서를 처음 생성하는 것보다 지속적으로 최신 상태로 유지하는 것이 더 어렵다. OpenWiki는 코드 저장소 변경 사항을 자동으로 감지하고 문서를 업데이트하여 사용자가 수동으로 개입할 필요 없도록 설계되었다. 이를 위해 GitHub Actions 워크플로를 자동으로 생성한다 [4:43].

에이전트 전용 문서의 특성: 조각 단위 검색과 컨텍스트 창 최적화

에이전트 전용 문서는 사람을 위한 문서와 매우 다른 특성을 가진다 [2:52].

  • 조각 단위 검색: 에이전트는 전체 문서 페이지나 디렉토리를 읽기보다 특정 조각(fragment)을 검색하여 정보를 얻는다 [3:22]. 따라서 모든 내용은 자족적(self-contained)이어야 한다.
  • 정확한 제목과 필터링: 예측 가능하고 정확한 제목은 에이전트가 정보를 필터링하고 검색하는 데 필수적이다 [3:33].
  • 컨텍스트 창 최적화: 에이전트의 컨텍스트 창(context window)에 맞게 최적화해야 한다. 불필요하게 많은 토큰을 소모하는 이미지 인코딩(base64 string) 등은 피해야 한다 [3:43]. 사람 문서처럼 서사, 배경 설명, 스크린샷, 동영상 등은 에이전트에게 불필요하거나 비효율적일 수 있다.

OpenWiki가 만드는 문서의 구조와 핵심 요소: OKF와 문서 간 연결

OpenWiki는 Karpathy의 LLM 위키와 유사하게 마크다운(Markdown) 파일을 생성한다 [5:02].

  • Quickstart.md: 에이전트가 저장소의 전체적인 개요를 파악하도록 돕는 최상위 문서이다 [5:11].
  • 에이전트의 자율적 문서 구조: OpenWiki는 에이전트가 필요하다고 판단하는 디렉토리에 따라 문서를 분할하며, 문서마다 특정 주제에 집중하도록 유도한다 [5:23].
  • OKF (Open Knowledge Format): Google의 Open Knowledge Format 0.1(현재 0.2)을 채택하여 모든 마크다운 파일의 상단에 YAML 머리말(front matter)을 추가한다 [5:55]. 이 머리말은 type, title, description, resource tags, timestamp 등의 결정론적인 필드를 포함하며, 에이전트가 문서를 검색하고 필터링하는 데 매우 중요하다 [6:57].
  • index.md와 log.md: 각 디렉토리에는 해당 디렉토리의 모든 파일 색인을 제공하는 index.md가 있어 에이전트가 빠르게 내용을 파악할 수 있다 [6:07]. log.md는 변경 로그(change log) 역할을 하여 문서 변경 이력을 추적하며, 사람 개발자에게도 유용하다 [6:16].
  • 문서 간 링크: resource tags와 마크다운 링크를 통해 문서 간의 연결을 강조한다 [8:14]. 이는 에이전트가 관련 컨텍스트를 빠르게 발견하고 탐색하는 데 도움을 준다.

OpenWiki의 효과: 에이전트 효율성 증대와 토큰 소모 감소

초기 평가에 따르면 OpenWiki는 에이전트의 도구 호출(tool calls) 횟수, 검색(searches) 횟수, 출력(outputs) 횟수를 줄이는 등 더 간결한 에이전트 사용(more concise agent usage)을 가능하게 한다 [9:11]. Deep Sweet 벤치마크의 20가지 작업 중 OpenWiki를 사용했을 때 성공률이 7~8개에서 9~10개로 소폭 증가했고, 토큰 소모(token consumption)는 상당히 감소하는 것을 확인했다 [9:25]. 이는 OpenWiki 문서가 에이전트에게 더 나은 컨텍스트를 제공하여 코드 저장소를 효율적으로 탐색하고 변경할 수 있게 돕는다는 의미이다.

초기 예상 오류: 사람 또한 에이전트 문서를 읽고 싶어 한다

OpenWiki 개발 초기에는 오직 에이전트만이 문서를 읽을 것이라고 가정했다 [10:01]. 하지만 사용자들로부터 사람도 이 문서를 읽고 싶다는 피드백을 빠르게 받았다 [10:10]. 이는 엔지니어링 과정에서 사람의 역할이 여전히 중요하다는 사실을 상기시켜 주었다. 이러한 피드백을 반영하여 OpenWiki는 사람 친화적인 몇 가지 수정 사항을 적용했다 [10:28]. 가장 큰 변화는 다이어그램(diagrams) 추가였다 [10:30]. 다이어그램은 에이전트에게도 도움이 될 수 있지만, 특히 시퀀스 다이어그램, 상태 다이어그램, 순서도(flowcharts) 등을 통해 사람 사용자가 문서를 훨씬 쉽게 이해하도록 돕는다.

OpenWiki CLI의 작동 방식: 초기 설정(init)과 자동 업데이트(update)

OpenWiki CLI는 open wiki init과 open wiki update 두 가지 주요 명령어를 사용한다 [11:27].

  • open wiki init [11:32]: 저장소를 초기화할 때 사용한다.
    • 설정 마법사: API 키, 모델, 저장소에 대한 고수준 지침 등을 설정한다 [11:41].
    • 파일 자동 생성: GitHub Actions 워크플로를 생성하여 매일 크론 작업(cron daily)으로 위키가 자동 업데이트되도록 한다 [12:01]. 또한 agent.md 또는 claw.md 파일을 수정하여 에이전트에게 OpenWiki의 존재와 활용법을 알린다 [12:12].
    • Git 이력 분석: 단순히 현재 코드 저장소의 스냅샷만 읽는 것이 아니라 Git 이력(Git history)을 분석하여 코드 변경 과정과 커밋 메시지, 제목 등 더 깊은 맥락을 파악한다 [13:06].
    • 문서 작성 및 유효성 검사: 문서를 작성한 후, 모든 문서가 OKF 규격을 준수하는지 확인하는 결정론적 검증(deterministic pass)을 수행하고 index.md 및 change log를 자동 생성한다 [13:29].
  • open wiki update [13:52]: 위키를 업데이트한다. init 명령어가 작성한 GitHub Actions 스케줄에 따라 실행된다.
    • 변경 사항 확인: last update.json 파일을 통해 마지막 실행 이후 Git 이력(Git history)에 변경 사항이 있는지 확인한다 [14:00]. 변경이 없으면 업데이트를 건너뛴다.
    • 에이전트 실행 및 PR 생성: 변경 사항이 있으면 에이전트를 실행하여 Git 로그(Git log)를 기반으로 저장소를 업데이트한 후, 풀 리퀘스트(PR)를 생성한다 [14:16]. 사용자는 이 PR을 병합하여 위키를 최신 상태로 유지한다.

주요 통찰·논점

에이전트의 생산성 극대화를 위한 문서 설계

OpenWiki는 AI 에이전트가 코드 저장소와 상호작용하는 방식을 근본적으로 개선하려 한다. 에이전트가 코드 작성의 주요 주체가 되는 미래에 대비하여, 에이전트의 기억 문제를 해결하고 생산성을 극대화하는 문서 설계가 핵심이다. 이는 단순한 문서 생성을 넘어, 에이전트가 정보를 빠르고 효율적으로 검색, 필터링, 이해할 수 있도록 돕는 구조와 메커니즘을 제공하는 데 중점을 둔다. 문서의 자족성, 정확한 메타데이터, 컨텍스트 창 최적화 등은 에이전트가 정보의 바다에서 길을 잃지 않도록 하는 중요한 장치이다.

문서 자동 생성보다 중요한 자동 유지보수

문서를 한 번 생성하는 것은 비교적 쉽지만, 그 문서를 최신 상태로 유지하는 것은 훨씬 어려운 문제이며, 이 지점에서 많은 문서화 프로젝트가 실패한다 [2:18]. OpenWiki는 이 문제를 해결하기 위해 자동 업데이트 메커니즘에 많은 비중을 둔다. GitHub Actions를 통한 일일 크론 작업, Git 이력 분석을 통한 변경 감지, 그리고 자동 풀 리퀘스트 생성 등은 개발자가 문서 유지보수에 거의 신경 쓰지 않고도 항상 최신 정보를 유지할 수 있게 한다. 이는 에이전트가 항상 정확하고 관련성 높은 정보를 기반으로 작업할 수 있도록 보장하는 핵심 요소이다.

OKF를 통한 에이전트 문서 검색 및 활용 효율 극대화

Google의 Open Knowledge Format (OKF) 채택은 OpenWiki의 중요한 설계 결정 중 하나이다 [6:57]. 문서 상단의 결정론적인 YAML 머리말에 type, title, description, resource tags, timestamp와 같은 구조화된 메타데이터를 포함함으로써, 에이전트가 문서를 단순한 텍스트 덩어리가 아닌 데이터베이스처럼 다룰 수 있게 한다 [7:33]. 이를 통해 에이전트는 특정 유형(type)의 문서만 필터링하거나, 특정 태그(tag)가 붙은 정보만 검색하는 등 검색 및 필터링 효율성을 극대화할 수 있다. 이는 방대한 코드 저장소 문서에서 에이전트가 필요한 정보를 정확하고 빠르게 찾아내도록 하는 핵심적인 기술이다.

인상적인 지점

개발 과정에서 오직 에이전트만이 문서를 읽을 것이라는 초기 가정이 실제 사용자 피드백을 통해 사람 또한 이 문서를 읽고 싶어 한다는 점으로 수정된 대목이 인상적이다 [10:01]. 이는 AI 에이전트가 많은 작업을 수행하더라도, 최종적으로는 사람 개발자와의 협업이라는 큰 틀 안에 존재한다는 사실을 보여준다. 에이전트 효율성에만 집중하다가 다이어그램 같은 사람 친화적인 요소의 필요성을 뒤늦게 깨달은 점은 기술 개발에서 사용자 경험(UX)의 중요성을 다시 한번 강조하는 사례이다. 아무리 에이전트가 뛰어나도, 그 에이전트와 함께 일하는 사람의 편의성을 간과해서는 안 된다는 교훈을 준다.
