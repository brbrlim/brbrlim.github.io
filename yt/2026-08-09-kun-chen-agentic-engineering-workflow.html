TL;DR

전 Meta, Microsoft, Atlassian 수석 엔지니어였던 Kun Chen은 대규모 언어 모델(LLM) 에이전트를 활용하여 하루 40~50개의 코드를 배포하는 효율적인 에이전트 공학 작업 흐름을 소개한다. 이 작업 흐름은 터미널 중심의 개발 환경, 에이전트의 기억과 기술 관리, Lavish Axi를 통한 시각적 기획, No Mistakes 파이프라인을 통한 자동화된 품질 관리, 그리고 여러 에이전트를 총괄하는 First Mate라는 상위 에이전트를 통해 생산성을 극대화한다. 이 영상은 에이전트를 단순한 도구가 아닌 자율적인 팀원으로 활용하여 개발자가 더 전략적인 역할에 집중할 수 있도록 돕는 실용적인 방법을 제시한다.

풀시청 판단

이 영상은 에이전트 기반 개발 작업 흐름을 구축하려는 숙련된 개발자, 특히 터미널 중심 환경에 익숙하거나 관심 있는 사람들에게 매우 유용하다. 화자가 직접 개발한 다양한 오픈소스 도구와 이들을 유기적으로 연결하여 생산성을 극대화하는 방식은 실무적인 통찰을 제공한다.

이런 사람에게 추천한다:

  • 에이전트 공학 실무자 및 연구자: 에이전트를 대규모로 활용하여 코드를 생산하고 관리하는 구체적이고 검증된 작업 방식을 배우고 싶다면 필히 시청해야 한다.
  • 고도로 효율적인 개발 환경에 관심 있는 사람: 터미널, Vim, tmux 등 키보드 기반의 개발 환경 최적화에 관심이 있다면 화자의 심도 있는 개인 설정과 철학에서 많은 영감을 얻을 수 있다.
  • AI 모델 기반 개발의 잠재력을 탐구하는 사람: 에이전트의 현재 한계(예: 개발 비용 편향성, 단위 테스트 선호)를 이해하고 이를 보정하는 방법을 알고 싶다면 도움이 된다.

영상의 약점 및 한계:

  • 특정 도구 의존성: 화자가 개발한 Axi, Lavish Axi, No Mistakes, Goodnight Have Fun, Treehouse, First Mate 등 독점적이고 커스터마이징된 도구들에 대한 의존도가 높다. 이 도구들을 직접 사용하지 않는다면 개념적 이해는 가능하지만, 실질적인 적용에는 추가적인 학습과 구현 노력이 필요하다.
  • 터미널 중심 환경에 대한 높은 숙련도 요구: Vim, tmux와 같은 터미널 도구에 대한 사전 지식이나 숙련도가 없으면 초반부 "선박 조립" 섹션을 이해하기 어려울 수 있다. 비록 GUI 사용자에게도 적용 가능하다고 언급했으나, 영상의 상당 부분이 터미널 환경에 맞춰져 있다.
  • 깊이의 편차: 일부 개념은 깊이 있게 설명하지만, 다른 개념(예: Axi의 10가지 원칙 전체)은 간략하게 소개하고 블로그 게시물로 링크하는 등 설명의 깊이가 일정하지 않다.
  • 빠른 기술 변화: 에이전트 기술은 빠르게 발전하므로, 영상에서 언급된 특정 에이전트 도구(예: Cloud Code)나 버전별 기능은 시간이 지남에 따라 변동될 수 있다.

핵심 내용

선박 조립: 생산성을 극대화하는 터미널 중심 개발 환경

화자의 에이전트 공학 작업 흐름은 터미널 중심의 환경에서 시작한다. 키보드에서 손을 떼지 않고 [2:41] 작업 흐름에 집중하며, 모든 환경(PC, 휴대폰)에서 동일한 작업 방식을 유지하는 것이 핵심이다 [3:29]. 이를 위해 세 가지 주요 도구를 활용한다.

  • WezTerm (터미널 에뮬레이터) [3:55]: 크로스 플랫폼을 지원하며, Lua 스크립트를 통해 거의 모든 것을 설정할 수 있는 높은 맞춤 설정 기능을 제공한다. 설정 변경 시 즉시 핫 리로드되는 기능은 매우 편리하다 [4:54].
  • tmux (터미널 다중화기) [5:10]: 터미널을 여러 개의 분할 창(pane)과 탭(window)으로 나누어 여러 작업을 동시에 처리할 수 있게 한다. 특히 tmux 세션은 서버에 영속적으로 유지되므로 [6:02], 작업 중 연결이 끊기거나 다른 기기(노트북, 휴대폰)에서 접속해도 이전 작업 상태를 그대로 복원할 수 있다 [6:25].
  • Neovim (텍스트 편집기) [7:18]: Vim의 현대적인 버전으로, 키보드 단축키만으로 커서 이동, 스크롤, 편집 등 모든 작업을 수행하도록 설계되어 손이 키보드에서 벗어날 일이 없다 [7:29]. 다양한 플러그인을 통해 코드 검색, 파일 찾기 등의 기능을 확장하여 마우스 없이도 빠르게 탐색하고 편집할 수 있게 한다.

에이전트 숙련 과정: 기억 파일과 기술 활용

새로운 에이전트(승무원)는 우리의 작업 방식에 익숙하지 않으므로, 이들을 숙련시키는 과정이 필요하다 [11:25]. 화자는 이를 '기억 파일(memory files)'과 '기술(skills)'을 통해 달성한다. 모든 에이전트가 동일한 방식으로 학습할 수 있도록 작업 흐름은 에이전트 종류에 독립적으로 설계되었다 [11:06].

  • 전역 기억 파일 (Global Memory File) [11:40]: 모든 에이전트 세션에 로드되는 최소한의 정보(27줄)를 담고 있다 [12:14]. 개인적인 선호 사항이나 에이전트의 암묵적인 편향을 교정하는 지시를 포함한다. 예를 들어, AI 모델이 인간 개발자의 추정치에 기반하여 개발 비용을 과대평가하여 [13:33] 저품질 솔루션을 선택하는 경향을 "개발 비용에 너무 큰 비중을 두지 말라"는 지시로 바로잡는다 [14:04]. 또한 버그 수정 시 단위 테스트보다 엔드투엔드 테스트(E2E)를 우선하도록 지시한다 [14:10].
  • 프로젝트별 기억 파일 (Project-level Memory File) [14:51]: 특정 프로젝트에 대한 맥락, 저장소 구조, 용어, 핵심 구성 요소 작동 방식, 엔드투엔드 테스트 방법, 코딩 컨벤션 등을 담는다 [15:24]. 이 파일은 에이전트가 잘못된 작업을 할 때마다 수정하고, 이를 기억하도록 지시하여 점진적으로 에이전트의 지식을 쌓아 올린다 [15:52].
  • 기술 (Skills)과 점진적 노출 (Progressive Disclosure) [16:16]: 기억 파일의 내용이 너무 방대해져 토큰 낭비가 심해지는 것을 방지하기 위해, 조건부로 필요한 정보를 '기술'로 분리한다 [16:38]. 에이전트는 처음에는 기술의 간략한 설명만 로드하여 [18:10] 토큰을 아끼고, 특정 기술이 필요하다고 판단될 때만 전체 내용을 읽어 효율성을 높인다 [18:18].
    • 외부 기술 사용 주의 [18:40]: 인터넷에서 무작위로 기술을 설치하는 것은 보안 위험(API 키 유출 등)과 성능 저하를 초래할 수 있다 [18:50]. GitHub 스타 수가 많다고 해서 항상 유용하거나 검증된 것은 아니므로 [19:12] 신중해야 한다.

효율적인 에이전트와의 소통: 음성 입력과 Axi 도구 설계

에이전트와의 소통 방식과 사용하는 외부 도구의 효율성은 에이전트 공학의 생산성에 큰 영향을 미친다.

  • 음성 입력의 활용 [20:40]: 화자는 프롬프트를 입력할 때 타이핑 대신 음성 입력을 주로 사용하며, 이는 타이핑보다 약 3배 빠르다 [21:01]. Open Super Whisper라는 무료 오픈소스 앱을 활용하여 [21:40] 로컬에서 Whisper 모델을 구동하여 고품질의 음성 전사를 얻는다. URL이나 파일 경로 등은 여전히 타이핑을 사용한다 [21:56].
  • Axi: 에이전트 인체 공학에 최적화된 도구 설계 [23:16]: 에이전트가 사용하는 외부 도구의 설계 방식은 에이전트의 성능에 지대한 영향을 미친다. 화자는 에이전트를 일등 시민(first class citizen)으로 대하고 에이전트 인체 공학(agent ergonomics)에 최적화된 도구 설계 표준 Axi를 만들었다 [23:27].
    • GitHub Axi 벤치마크 결과, GitHub MCP 서버를 사용하는 것은 CLI 방식보다 토큰 비용이 3배 높고 지연 시간은 2배 이상 길었다 [22:50]. Axi를 적용하면 비용을 크게 줄이고 성공률을 높일 수 있다 [23:07].
    • 예를 들어, 토큰 효율적인 출력 형식을 사용하면 JSON 대비 약 40%의 토큰을 절약할 수 있다 [23:37]. 화자는 GitHub Axi, Chrome Dev Tools Axi 등의 Axi 도구를 개발하여 에이전트의 작업 효율을 높인다 [23:42].

생산성 확장: Lavish Axi를 통한 시각적 기획

복잡한 작업을 기획할 때 에이전트가 텍스트 위주로 계획을 제시하면 [26:13] 이해하기 어렵고 구체적인 피드백을 주기 어렵다. 이를 해결하기 위해 화자는 Lavish Axi라는 도구를 사용한다 [24:26].

  • Lavish Axi는 에이전트에게 HTML 아티팩트를 생성하도록 지시하여 [27:14], 계획이나 프로토타입을 시각적으로 표현한다 [27:01]. 이 아티팩트는 작업 중인 프로젝트의 디자인 시스템과 일관성을 유지하여 [27:19] 실제 앱과 유사한 모습으로 개념을 검토하고 프로토타입을 만들 수 있게 한다.
  • 사용자는 터미널로 돌아갈 필요 없이 [28:04], 이 시각적 인터페이스 내에서 특정 부분에 주석을 달고 [27:40] 피드백을 주거나 옵션을 클릭하여 결정을 내릴 수 있다 [27:56]. 이를 통해 기획 단계에서 요구 사항을 훨씬 명확하게 정의할 수 있어, 이후 구현 단계에서는 거의 개입할 필요가 없어진다 [28:30].

자동화된 품질 관리: No Mistakes 파이프라인

에이전트가 코드를 매우 빠르게 작성하기 때문에, 모든 변경 사항을 사람이 일일이 검토하면 병목 현상이 발생하고 [28:51] 재미도 없다. 화자는 자신을 엔지니어링 관리자나 디렉터로 생각하고 [29:21], 문화와 프로세스를 통해 품질을 확보한다.

  • No Mistakes 파이프라인 [29:50]: 이 무료 오픈소스 도구는 에이전트가 생성한 초벌 코드를 자동으로 검증하고 정제하여 깨끗한 풀 리퀘스트(PR)로 만든다 [30:00].

    • 핵심 단계: 변경 의도 파악, 최신 메인 브랜치에 리베이스 및 병합 충돌 해결 [30:20], 독립된 컨텍스트 창에서 '대립형 검토(adversarial review)' 수행 [30:32], 원래 의도에 대한 엔드투엔드 테스트 및 증거 자료 기록 [30:49] (스크린샷, 비디오 데모 등) [32:16], 관련 문서 업데이트 [31:02], 린팅 문제 확인 [31:08] 후 PR 발행.
    • PR 관리: No Mistakes는 PR이 병합될 때까지 [31:16] 병합 충돌이나 CI 파이프라인 오류를 자동으로 처리하며 "베이비시팅"한다 [31:22].

  • 인간 개발자의 역할: 개발자는 파이프라인이 완료되고 모든 검사가 통과될 때까지 다른 작업을 수행하며 [31:43] 최종 승인 여부를 결정한다. 저위험 변경 사항은 코드 변경 내용을 직접 확인하지 않고도 병합할 수 있어 [32:51] 인간 개발자의 개입을 줄이면, 개발자는 여러 작업을 동시에 시작할 수 있게 된다.

  • Goodnight Have Fun (장시간 작업 관리) [34:10]: 에이전트가 7~8시간 밤새 작업을 수행하게 할 때 유용한 무료 오픈소스 도구다 [34:07]. 특정 목표(예: 7세 아이처럼 앱을 사용하며 사용성 문제 발견 및 수정)를 설정하면, 에이전트는 정지 조건이 충족될 때까지 [34:22] 반복해서 작업을 실행한다 [35:01]. 페이지 로드 시간 단축, 엔드투엔드 테스트 커버리지 개선 등 검증 가능한 목표에 특히 적합하다 [35:39]. 토큰 사용량이나 반복 횟수 등을 정밀하게 제어할 수 있어 [36:05] 예기치 않은 비용 소모를 방지한다.

  • Treehouse (작업 트리 관리) [38:08]: 여러 에이전트가 동시에 동일한 저장소에서 작업할 경우 충돌이 발생할 수 있다 [36:40]. git worktree를 사용하면 저장소의 복제본을 만들어 [36:51] 독립적인 작업 환경을 제공하지만, 이를 수동으로 관리하는 것은 번거롭다 [37:31]. Treehouse는 이 git worktree를 자동으로 생성하고 관리해주는 도구다 [38:11]. 개발자는 Treehouse를 실행하여 새로운 작업 트리에 진입하고, 작업이 끝나면 탭을 닫기만 하면 된다. Treehouse는 사용하지 않는 작업 트리를 재활용하여 효율성을 높인다 [38:38].

  • 이러한 도구들을 활용하여 [39:59] 화자는 tmux의 여러 탭에서 Treehouse로 생성된 독립적인 작업 트리 내에 에이전트 세션을 세 개 동시에 실행하는 것을 시연한다. 이는 개발자가 여러 작업을 병렬로 진행할 수 있는 기반이 된다.

최상위 에이전트: First Mate를 통한 작업 위임

여러 에이전트 세션을 동시에 관리하는 것은 여전히 컨텍스트 전환을 유발하고 [40:31] 피로도를 높일 수 있다. 궁극적으로 화자는 '선장'으로서 [40:46]: 이 무료 오픈소스 프로젝트는 개발자가 '선장'처럼 지시를 내리면, 그 지시를 받아 여러 하위 에이전트(승무원)들을 총괄 관리한다 [41:22]. First Mate는 tmux 탭을 열고, Treehouse를 호출하여 작업 트리를 생성하며, 그 안에서 에이전트를 실행하고, No Mistakes 파이프라인을 통해 작업을 검증하는 등 [42:43] 모든 과정을 자동화한다.

  • 화자는 First Mate에게 한 번의 지시(예: 세 프로젝트에 CLI 업데이트 명령 추가)로 여러 병렬 작업을 동시에 시작하도록 지시하고 [42:58], First Mate는 이 모든 작업을 대신 관리하여 개발자의 부담을 크게 줄인다 [43:08].
  • 음성 전사 정확도 향상 [41:22]: Open Super Whisper의 '초기 프롬프트(initial prompt)' 기능에 자주 사용하는 프로젝트 이름이나 전문 용어를 입력하면 [42:01], 음성 인식의 정확도를 크게 높일 수 있다 [42:08].
  • 이로써 개발자는 세부적인 작업 관리가 아닌 [44:06], 사용자 이해, 경쟁 환경 분석, 전략적인 '보물 지도' 작성 등 더 중요한 상위 수준의 문제 해결에 집중할 수 있게 된다 [44:46].

주요 통찰·논점

AI 개발 비용 편향성 교정: 인간 중심의 판단 오류 극복

AI 모델은 인간의 데이터를 기반으로 훈련되었기 때문에 [13:35], 실제 AI는 몇 분 만에 플레이 가능한 버전을 만들어낼 수 있다 [13:26]. 이러한 편향은 AI가 저품질, 확장성 부족, 유지보수 어려운 '값싼' 솔루션을 선택하게 만들 수 있다 [13:56]. 따라서 화자는 전역 기억 파일에 "기술적 결정 시 개발 비용에 너무 큰 비중을 두지 말라"는 명시적인 지시를 추가하여 [14:04]. 인터넷에서 쉽게 구할 수 있는 '기술'들은 에이전트에게 임의의 코드를 실행하도록 지시할 수 있으며 [18:51], 이는 API 키나 은행 계좌 자격 증명과 같은 민감한 정보를 외부로 유출할 심각한 보안 위험을 초래한다 [18:56]. 또한, 일부 인기 있는 기술들은 실제로 에이전트의 성능을 저하시켜 [19:08] 토큰 사용량을 늘리고 결과 품질을 떨어뜨리는 것으로 벤치마크를 통해 입증되기도 했다 [19:32]. 따라서, 엄격하게 검증되지 않은 외부 기술은 사용하지 않고 [20:16] 스스로 만들거나 신뢰할 수 있는 소스만을 활용하는 것이 중요하다.

에이전트와의 협업 방식 전환: 엔지니어링 관리자 관점

AI가 코드를 작성하는 속도가 빨라짐에 따라, 인간 개발자가 모든 코드를 일일이 검토하는 방식은 비효율적인 병목 현상으로 작용한다 [28:51]. 화자는 이 문제 해결을 위해 개발자가 스스로를 '엔지니어링 관리자'나 '디렉터'로 인식하는 [29:21] 관점의 전환을 제안한다. 관리자는 모든 PR을 직접 검토하기보다 좋은 문화와 프로세스를 구축하여 [29:30] 팀의 품질을 높이는 데 집중한다. 마찬가지로, 개발자는 Lavish Axi를 통해 초기에 요구 사항을 명확히 계획하고 [33:00], No Mistakes 파이프라인을 통해 에이전트가 자동화된 검증을 거치도록 한 후 [33:05], 최종 단계에서 품질 기준을 유지하는 역할에 집중한다 [32:51]. GitHub MCP 서버가 CLI 방식보다 토큰 비용이 3배 높고 지연 시간이 2배 이상 길다는 벤치마크 결과는 [22:50] 단순한 도구 선택이 아니라 도구 자체의 '에이전트 인체 공학'적 설계가 얼마나 중요한지 보여준다. 화자가 만든 Axi 표준은 토큰 효율적인 출력 형식을 통해 [23:37] JSON 대비 40%의 토큰을 절약하는 등, 에이전트의 작업 효율을 극대화하기 위한 도구 설계 원칙의 중요성을 역설한다. 이는 에이전트 공학에서 도구를 '어떻게' 사용하는 것만큼 '어떻게' 설계하는지가 중요함을 시사한다.

생산성 병목 현상의 이동: 에이전트 활용의 궁극적 목표

First Mate와 같은 상위 에이전트를 도입하여 대부분의 작업을 위임하게 되면 [43:08], 개발자는 세부적인 작업 관리에서 완전히 해방된다. 이때 흥미로운 현상은 '무엇을 지시해야 할지 아이디어가 고갈된다'는 것이다 [44:31]. 이는 개발자의 생산성 병목 현상이 더 이상 '작업 수행'에 있지 않고 [44:36], '무엇을 할 것인가'라는 전략적인 의사결정으로 이동했음을 의미한다 [44:40]. 즉, 개발자는 사용자 이해, 경쟁 환경 분석, 그리고 팀을 올바른 방향으로 이끌 '보물 지도'를 그리는 등 [44:46].

인상적인 지점

  • "AI가 자신이 인간보다 코드를 훨씬 빠르게 작성할 수 있다는 것을 아직 모르는 것 같다" [13:43]: AI 모델이 훈련 데이터의 인간 개발자 편향을 답습하여 자신의 실제 개발 속도를 과소평가한다는 지적은 매우 반직관적이면서도 중요한 통찰이다. 이를 바로잡기 위해 전역 기억 파일에 명시적인 지시를 추가하는 것은 AI의 잠재력을 온전히 활용하기 위한 필수적인 단계로 보인다.
  • "마우스로 전환하면 흐름이 끊기고 뇌가 컨텍스트 전환을 하게 된다" [2:52]: 키보드에 손을 두는 것이 얼마나 중요한지 강조하는 부분은 매우 설득력 있다. 이 작은 습관이 작업 흐름을 유지하고 뇌의 불필요한 컨텍스트 전환을 막아 생산성을 높인다는 설명은 많은 개발자에게 공감을 줄 것이다.
  • "아무도 '나는 매일 diff를 검토하는 것을 좋아해서 엔지니어가 되었다'고 말하지 않는다" [29:11]: 코드 검토가 지루하고 생산성 병목의 원인이 된다는 솔직한 언급은 개발자의 고충을 정확히 짚어낸다. 이를 해결하기 위해 No Mistakes 파이프라인과 같은 자동화된 도구를 구축하고, 개발자가 더 고차원적인 역할로 전환해야 한다는 주장의 핵심을 보여준다.
  • "First Mate가 너무 많은 일을 처리해주면 무엇을 시킬지 아이디어가 고갈되기 시작한다" [44:31]: 에이전트 활용으로 생산성 병목 현상이 '전략적 사고'로 이동한다는 결론은 에이전트 공학의 궁극적인 지향점을 명확히 보여준다. 개발자가 단순 작업에서 벗어나 더 큰 그림을 그려야 한다는 메시지는 미래 개발자의 역할에 대한 중요한 시사점을 던진다.
