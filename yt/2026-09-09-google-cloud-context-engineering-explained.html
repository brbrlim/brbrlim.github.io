TL;DR

많은 개발자가 AI 모델의 성능을 높이기 위해 프롬프트를 길게 작성하지만, 이는 올바른 접근 방식이 아니다. 콘텍스트 엔지니어링은 모델이 각 단계에서 필요한 정보를 선별적으로 제공하고 불필요한 정보는 제외하여, 모델이 더 신뢰할 수 있고 스마트한 답변을 생성하도록 돕는 기술이다. 이는 프롬프트 엔지니어링의 진화된 형태로, 모델의 제한된 작업 기억 공간을 효율적으로 관리하는 것이 핵심이다.

풀시청 판단

이 영상은 AI 시스템, 특히 에이전트(Agent)를 개발하는 모든 개발자에게 유익하다. 복잡한 AI 애플리케이션의 성능 저하 원인 중 하나인 콘텍스트 관리의 중요성을 이해하고, 이를 개선하기 위한 구체적인 방법론을 배우려는 사람에게 풀시청을 권한다.

이 영상은 프롬프트 엔지니어링에 익숙하지만, 모델의 답변 정확도와 신뢰성을 높이는 데 어려움을 겪는 개발자에게 특히 가치가 있다. 모델의 '작업 기억'을 효율적으로 관리하는 방법을 이해함으로써, 더 견고하고 유용한 AI 애플리케이션을 구축하는 데 필요한 실제적인 지식과 전략을 얻을 수 있다.

약점·한계: 이 영상은 콘텍스트 엔지니어링의 개념과 필요성, 그리고 기본적인 4단계 방법론을 잘 설명하지만, 각 단계의 기술적인 깊이나 구현 세부 사항까지는 다루지 않는다. 실제 코드 예시나 복잡한 아키텍처 다이어그램보다는 개념 설명과 비유에 집중하므로, 심층적인 기술 구현 방법을 찾고 있다면 추가 자료를 찾아봐야 한다. 또한, 빠르게 발전하는 AI 분야의 특성상 이 영상에서 제시하는 모범 사례가 시간이 지남에 따라 업데이트될 수 있음을 고려해야 한다.

핵심 내용

콘텍스트 엔지니어링은 프롬프트 엔지니어링을 넘어선 접근법이다

대부분의 개발자는 AI 모델의 부정확한 답변을 개선하기 위해 프롬프트를 길게 작성하는 경향이 있다 [0:04]. 이는 모델의 콘텍스트 창(context window)을 불필요한 정보로 채워 정확도를 떨어뜨리는 잘못된 방식이다 [1:53]. 프롬프트 엔지니어링이 질문의 표현과 구조화에 초점을 맞춘다면 [3:04], 콘텍스트 엔지니어링은 모델이 작업을 수행할 수 있도록 제공하는 모든 정보, 즉 시스템 메시지, 도구, 검색된 사실, 메모리, 형식 규칙 등을 선별하고 조립하는 기술이다 [1:08]. 이는 업계 전체에서 중요성이 강조되는 변화로, 완벽한 프롬프트를 작성하는 것에서 모델의 행동을 올바른 방향으로 이끄는 '최소한의 고신호 토큰(high-signal tokens) 집합'을 큐레이션하는 방식으로 전환되고 있다 [1:20].

AI 모델의 정확도를 떨어뜨리는 4가지 콘텍스트 실패 양상

모델의 콘텍스트 창이 길어진다고 항상 더 좋은 결과를 내는 것은 아니다. 오히려 오류가 침투하거나 무관한 텍스트에 주의가 분산될 때, 또는 두 정보가 서로 모순될 때 정확도가 떨어질 수 있다 [1:53]. 특히 에이전트(Agent)의 경우 대화와 도구의 출력이 눈덩이처럼 불어나면서 다음과 같은 4가지 일반적인 실패 양상이 나타난다.

  1. 오염(Poisoning): 잘못된 사실이 콘텍스트에 삽입되어 반복적으로 재사용될 때 발생한다 [2:22]. 이는 모델의 신뢰도를 크게 떨어뜨린다.
  2. 주의 분산(Distraction): 모델이 새로운 계획을 수립하기보다 방대한 과거 기록에 고착되어 불필요한 정보에 집중할 때 나타난다 [2:32].
  3. 혼란(Confusion): 불필요하거나 무관한 세부 정보가 모델을 잘못된 답변으로 유도할 때 발생한다 [2:40].
  4. 충돌(Clash): 콘텍스트 내 두 정보 출처가 서로 모순되어 모델이 잘못된 정보를 선택할 때 나타난다 [2:46].

이러한 실패 양상을 이해하는 것은 문제를 진단하고 해결하는 데 중요한 첫걸음이다 [2:52].

모델의 제한된 기억력을 채우는 7가지 콘텍스트 구성 요소

AI 모델은 제한된 단기 기억을 가진 두뇌와 같으므로, 다음 단계에 필요한 모든 것을 효율적으로 제공해야 한다 [3:32]. 현재 대부분의 모델에 사용되는 콘텍스트 스택은 다음 7가지 구성 요소로 이루어진다.

  1. 지침(Instructions): 시스템 프롬프트 및 가이드라인으로, 명확하고 평이한 언어로 작성하는 것이 중요하다 [3:49].
  2. 사용자 입력(User input): 사용자가 현재 요청하는 내용이다 [3:57].
  3. 검색된 사실(Retrieved facts): 가장 중요한 정보 조각들로, 외부 저장소에서 가져온다 [4:02].
  4. 도구(Tools): 모델이 호출할 수 있는 함수와 이에 대한 설명이다 [4:08].
  5. 단기 기록(Short-term notes): 최근 단계를 요약하여 모델이 최근 변경 사항을 기억하도록 돕는다 [4:16].
  6. 장기 기억(Long-term memory): 사용자나 프로젝트에 대한 안정적인 사실을 포함하며, 필요에 따라 선택적으로 제공된다 [4:27].
  7. 출력 형식(Output format): 답변의 형태를 고정하는 스키마나 예시를 제공하여 일관된 출력을 보장한다 [4:34].

이 구성 요소들을 적절히 조합하고 관리하는 것이 콘텍스트 엔지니어링의 핵심이다.

Log Look 에이전트 구축 예시: 콘텍스트 엔지니어링의 실제 적용

'Log Look'이라는 간단한 에이전트를 구축하는 예시를 통해 콘텍스트 엔지니어링의 실제 적용 방식을 설명한다 [4:43]. Log Look은 보안 경고를 분류하고 한 단락 요약 및 심각도 점수를 초안으로 작성하는 도우미이다 [4:50]. 일반적인 챗봇 방식("오늘 로그 분석해서 문제 알려줘")으로는 무작위 추측을 내놓을 수 있지만 [5:01], 콘텍스트 엔지니어링을 적용하면 훨씬 더 안정적이고 정확한 답변을 얻을 수 있다.

Log Look 에이전트에는 다음과 같은 콘텍스트가 제공된다 [5:12].

  • 시스템 지침: "사건을 한 단락으로 요약하고 0에서 4 사이의 심각도 점수를 부여해라. 제공된 콘텍스트만 사용하고, 데이터가 누락되면 특정 파일 경로를 요청해라." [5:18]
  • 도구 목록: 파일 읽기, grep(로그 검색), 알려진 오탐(false positives) 조회 등의 도구를 제공한다 [5:37].
  • 검색된 사실: 오늘 로그 중 오류 또는 심각 수준의 최근 한 시간 내 기록과 팀의 오탐 목록만 선별하여 제공한다 [5:49].
  • 단기 기록: "이 파일은 이미 확인했다. 다음으로 이 로그를 스캔해라."와 같은 최근 수행 단계를 요약하여 전달한다 [6:09].
  • 형식: 입력과 출력 모두 JSON 형식을 기대하도록 설정한다 [6:21].

동일한 모델이라도 이처럼 체계적인 콘텍스트를 제공하면 훨씬 우수한 성능을 발휘한다 [6:27].

주요 통찰·논점

콘텍스트 엔지니어링의 4단계: 기록, 선택, 압축, 격리

콘텍스트 엔지니어링은 다음 4가지 간단한 단계를 통해 효과적으로 수행할 수 있다 [6:32]. 이 단계들은 최고의 에이전트 시스템에서 공통적으로 나타나는 특징이다 [6:35].

  1. 기록(Write): 콘텍스트 창 외부에 메모를 저장한다. [6:45] 에이전트가 계획, 중간 결과, 미해결 질문 등을 스크래치 패드(scratch pad)에 보관하도록 한다 [6:51]. 이 정보를 매 호출마다 콘텍스트에 전부 넣는 대신 외부에 유지하고 필요할 때만 불러온다. 이는 작업 콘텍스트를 깨끗하게 유지하면서도 기억을 보존하는 방법이다. Log Look 에이전트의 경우, 확인된 항목 목록을 담은 investigation_steps.md와 같은 파일을 사용하여 조사 단계를 기록할 수 있다 [7:12].
  2. 선택(Select): 현재 중요한 것만 가져온다. [7:27] 검색 기능을 활용하여 현재 단계에 필요한 로그 조각이나 정책 라인 등 필수적인 정보만 가져온다 [7:30]. 키워드와 의미론적 검색을 모두 포함하는 하이브리드 검색(hybrid retrieval)이 복잡한 로그에서는 임베딩 기반 검색보다 우수할 때가 많다 [7:38]. 중요한 것은 모든 것을 저장하는 것이 아니라 '선택'하는 것이다 [7:47]. Log Look 에이전트는 최상위 N개의 오류 발생과 런북(runbook)에서 심각도 점수와 관련된 특정 섹션만 선택할 수 있다 [7:50].
  3. 압축(Compress): 신호는 유지하고 나머지는 버린다. [8:00] 긴 기록은 주기적으로 짧고 손실 없는 메모로 요약하고 새로운 콘텍스트 창으로 진행한다 [8:06]. 이는 최근 몇 개의 원본 항목은 안전을 위해 유지하면서도, 방대한 채팅 기록을 계속 끌고 다니는 비효율성을 방지한다 [8:16]. Log Look 에이전트는 최근 5개의 발견 사항은 유지하고, 그보다 오래된 모든 정보는 3줄 요약으로 압축할 수 있다 [8:25].
  4. 격리(Isolate): 소스들을 샌드박스 처리하여 간섭을 피한다. [8:34] 큰 작업을 하위 에이전트(sub-agents)나 단계(phases)로 분할한다 [8:42]. 각 하위 에이전트는 자체 콘텍스트를 탐색한 후 짧은 요약을 코디네이터에게 반환한다 [8:45]. 이는 도구 간 정보 유출을 줄이고, 하나의 노이즈가 많은 소스가 다른 소스를 오염시키는 것을 방지한다 [8:52]. Log Look 예시에서는 리더(reader) 하위 에이전트가 사실을 추출하고, 스코어러(scorer) 하위 에이전트가 정책을 적용하며, 라이터(writer) 하위 에이전트가 이들의 요약을 바탕으로 최종 요약을 구성한다 [8:59].

이러한 4단계 접근 방식은 단순한 챗봇을 넘어 복잡한 AI 에이전트를 구축하는 데 필수적인 기술이다 [9:33].

인상적인 지점

"콘텍스트를 방대한 프롬프트를 쏟아붓는 대신 큐레이션해야 한다는 점을 기억하는 것이 중요하다"는 메시지 [9:13]는 이 영상의 핵심을 관통한다. 모델의 콘텍스트 창이 무한히 커진다 해도, '양'보다는 '질'과 '선별'이 중요하다는 점을 강조한다. 이는 직관과는 다를 수 있지만, 모델이 제한된 작업 기억을 효율적으로 사용하게 하는 근본적인 원칙이다.
