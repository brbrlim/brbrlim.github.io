TL;DR

이 강연은 대규모 언어 모델(LLM) 기반 인공지능(AI) 에이전트가 인간 소프트웨어 엔지니어의 작업을 수행하는 시스템을 구축하는 과정을 단계별로 설명한다. 단순한 LLM 호출부터 시작해 피드백 루프, 도구 사용, 단일 에이전트, 나아가 다중 에이전트 시스템으로 발전하며 각 단계의 이점과 한계를 다룬다. 특히 생산 시스템 운영의 복잡성 해결에 초점을 맞춰 에이전트가 문제를 진단하고 해결하는 실제 사례와 학습 및 평가 방법을 제시한다.

풀시청 판단

이 영상은 소프트웨어 엔지니어링, 특히 대규모 운영 시스템 관리 및 문제 해결에 AI 에이전트를 적용하는 방법과 관련 기술의 현재 상태, 미래 방향에 관심 있는 사람에게 매우 유용하다. ML 엔지니어, 소프트웨어 개발자, 시스템 아키텍트 등 에이전트 시스템 설계 및 구현에 관심 있는 실무자라면 전체 시청을 통해 각 단계별 복잡성 증가에 따른 기술적 요구 사항과 해결책을 깊이 이해할 수 있다.

  • 추천 시청자:

    • LLM 기반 에이전트 시스템 개발자: 단순 LLM 호출부터 다중 에이전트 시스템까지 복잡성을 점진적으로 높이는 과정을 통해 각 구성 요소의 설계 원칙과 한계 극복 방법을 배울 수 있다.
    • 소프트웨어 운영 엔지니어(SRE): 실제 서비스 장애 상황(UI 지연, API 오류, 결제 시스템 장애)을 에이전트가 어떻게 진단하고 해결하는지 구체적인 시연을 통해 살펴볼 수 있다.
    • 시스템 아키텍트: 다중 에이전트 시스템의 분산 설계 패턴(스캐터-개더, 오케스트레이터 루프, 자유형), 컨텍스트 관리, 상태 유지 방식 등 복잡한 시스템 구축을 위한 고려 사항을 얻을 수 있다.

  • 얻게 될 통찰:

    • LLM 기반 에이전트가 소프트웨어 엔지니어링 문제를 해결하는 실제 데모를 통해 직관적인 이해를 얻는다.
    • 단일 LLM 호출의 한계점과 이를 극복하기 위한 액터-비평가 시스템, 도구 사용, 계획 및 실행 루프가 어떻게 추가되는지 학습한다.
    • 다중 에이전트 시스템의 필요성, 설계 패턴, 컨텍스트 및 상태 관리 방식, 학습 전략(후속 훈련, 외부 기억)에 대한 구체적인 논의를 들을 수 있다.
    • 현재 에이전트 시스템의 주요 기술적 한계(추론 능력, 컨텍스트 창, 도구 인터페이스, 사람의 병목 현상)와 미래의 발전 방향에 대한 심도 있는 관점을 접한다.

  • 약점 및 한계:

    • 소프트웨어 엔지니어링 도구 사용에 대한 구체적인 코드 예시보다는 개념적 설명과 데모 화면 위주로 진행된다. 실제 구현 세부 사항보다는 아키텍처와 원리에 집중한다.
    • 언급된 "GPT-5"의 드롭은 실제와 다르다. (영상 촬영 시점과 현재 시점의 차이).
    • 일부 질문-답변 세션은 다소 비정형적이거나 추상적인 질문에 대한 일반적인 답변으로 이뤄진다.

핵심 내용

인간 소프트웨어 엔지니어의 작업은 코딩 그 이상이다

소프트웨어 엔지니어링은 단순히 코드를 작성하는 것을 넘어, 대규모 생산 시스템을 구축하고 운영하는 복잡한 과정이다 [1:21]. 연사들은 과거 경험을 통해 엔지니어링 팀의 대다수 시간이 새로운 기능 개발보다 기존 시스템 유지 보수 및 안정성 확보에 사용된다는 사실을 지적한다 [2:11]. 사용자는 기능 지연보다 시스템 장애에 더 크게 불평하기 때문에, 안정적인 시스템 운영은 핵심적인 과제다 [2:20]. 그러나 대규모 시스템의 복잡성은 동적으로 변화하는 환경, 수많은 도구, 그리고 문서화되지 않은 조직 내부 지식 등으로 인해 기하급수적으로 증가한다 [4:46]. 이러한 복잡성 속에서 AI 에이전트가 인간 엔지니어의 작업을 돕는 새로운 해결책으로 부상하고 있다.

소프트웨어 엔지니어링 AI 에이전트의 진화

AI 도구의 발전은 단순한 코드 자동 완성에서 시작하여, 점차 복잡한 작업을 자율적으로 수행하는 에이전트 시스템으로 진화하고 있다 [3:09].

  1. 초기 단계: AI는 주로 코드 자동 완성(autocompletion)이나 코드 생성과 같은 보조적인 역할에 머물렀다.
  2. 단일 에이전트 시스템: 특정 작업을 수행하도록 지시받은 에이전트가 결과물을 생성한다. 여전히 인간이 여러 에이전트 또는 도구 사이의 연결 고리(glue) 역할을 한다 [3:51].
  3. 다중 에이전트 시스템: 인간으로부터 상위 수준의 지시를 받아 여러 에이전트가 상호 작용하며 계획을 세우고, 반복적으로 추론하며, 다양한 도구(코드, 생산 시스템 측정 도구, 인프라 상호 작용 등)를 활용하여 문제를 해결한다 [4:10].

Resolve 시스템 데모는 이러한 다중 에이전트 시스템의 실제 적용 사례를 보여준다. 예를 들어 "오늘 아침 UI가 느려졌다"는 상위 수준의 지시를 받으면 [6:48], 에이전트는 자체적으로 계획을 수립하고, 다양한 도구(Datadog, Kubernetes, Slack, GitHub 등)를 활용하여 프런트엔드 서비스의 지연 원인을 분석한다 [7:34]. 데모에서는 Cron 작업으로 인해 의도적으로 활성화된 기능 플래그가 원인인 '카오스 엔지니어링' 상황을 에이전트가 찾아내고 [9:56], 해결 명령까지 제시하는 모습을 시연한다 [11:41]. 더 나아가 에이전트는 Slack 채널에서 발생하는 알림에 자동으로 응답하고 [12:17], 근본 원인(예: 비효율적인 N+1 쿼리 문제)과 코드 수정 방안까지 제시하는 온콜(on-call) 엔지니어 역할을 수행할 수 있다 [13:08].

LLM 기반 에이전트 시스템의 구축 — 복잡성 계층

다중 에이전트 시스템을 구축할 때 가장 중요한 원칙은 "단순하게 유지하는 것"이다 [17:04]. 모든 문제가 복잡한 시스템을 요구하지 않으며, 특정 작업에 맞는 적절한 복잡성 수준을 찾아야 한다. 에이전트 시스템은 다음의 단계로 복잡성을 더하며 발전한다.

1. 단일 LLM 호출 (Single-pass LLM call)

가장 기본적인 형태로, 하나의 프롬프트가 들어가고 하나의 응답이 나온다 [18:23]. 올바른 입력과 프롬프트, 정확한 출력 해석이 가능하다면 의외로 많은 경우에 작동한다 [18:31].

  • 예시: 결제 시스템 장애 발생 시, LLM에 1,000줄의 로그를 제공하고 "왜 결제가 실패하는가?"라고 질문하면 [19:25], LLM이 "카드 만료" 로그 메시지를 찾아 원인으로 지목할 수 있다 [19:33].
  • 한계: 내부 피드백 루프가 없어 응답을 평가하거나 개선할 수 없다. 추론 과정이 반복되지 않고, 불확실성에 대한 개념도 없어 무작정 첫 답변을 신뢰해야 하는 문제가 발생한다 [20:09].

2. 액터-비평가 시스템 (Actor-Critic system)

단일 LLM의 한계를 극복하기 위해 피드백 루프를 추가한다 [20:41]. 액터(Actor) LLM이 후보 솔루션을 제안하면 비평가(Critic) LLM이 이를 평가하고 피드백을 제공한다. 비평가가 승인하면 솔루션을 반환하고, 아니면 액터에게 피드백과 함께 재시도를 요청한다 [20:53].

  • 예시: 액터가 "카드 만료"를 원인으로 지목하면, 비평가는 "카드 만료는 일회성 현상이며 광범위한 장애를 설명하기 어렵다"고 지적한다 [21:32]. 액터는 이 피드백을 반영하여 답변을 수정한다.
  • 한계: 여전히 사용자가 제공한 초기 로그에만 의존하며 새로운 데이터를 조회하거나 탐색할 수 없다. 영구적인 기억이 없어 반복적인 작업에서 과거 상태를 잊어버리고 무한 루프에 빠질 수 있다. 컨텍스트 창 제한, 수학 능력 부족, 환각 현상 등 LLM 자체의 근본적인 한계도 존재하며, 외부 지식에 접근할 수 없다 [22:01].

3. 도구 사용 LLM (LLM with Tool Use)

LLM이 외부 환경과 상호 작용할 수 있도록 "도구(Tool)" 개념을 도입한다 [22:43]. 도구는 데이터베이스 조회, 계산기 호출, 사용자에게 추가 질문하기 등 외부 함수를 의미한다 [22:49]. 도구는 환경 상호 작용, 기억, 수학 능력, 외부 지식 접근 등 액터-비평가 시스템의 여러 한계를 해결한다 [23:01].

  • 도구 정의: 각 도구는 이름, 설명, 입력 스키마(매개변수)를 가지며, LLM은 구조화된 출력(예: JSON)으로 도구 호출을 수행한다 [23:18]. 실행 엔진이 도구를 실행하고 결과를 LLM에 반환하면, LLM은 이를 바탕으로 다음 행동을 결정한다 [23:57].
  • 예시: 사용자가 로그를 직접 붙여 넣지 않고 "결제 실패, 로그 확인"이라고만 지시하면 [24:46], LLM은 스스로 어떤 로그를 확인할지, 어떤 로그 쿼리를 작성할지 결정하여 Loki 시스템에 도구 호출을 보낸다. 반환된 로그를 분석하여 Stripe 연결 관련 네트워크 문제를 찾아낸다 [25:07].
  • 한계: 여전히 상태 추적(state tracking) 능력이 부족하여 변화하는 작업 상태를 관리하기 어렵다. 도구 호출 실패를 제대로 처리하지 못하거나, 상위 목표에 대한 실제 계획 없이 반응적으로만 도구를 사용하는 경향이 있다 [25:46].

4. LLM 에이전트 (LLM Agent)

도구 사용 LLM에 '계획(planning)' 루프와 '자율 실행(autonomous execution)' 엔진을 추가하여 에이전트다운 면모를 갖춘다 [26:32]. 에이전트는 지시를 받고 추론하여 계획을 세우고, 도구 호출(행동)을 수행하며, 결과를 관찰하고, 다시 계획을 수정하는 과정을 반복하여 목표를 달성한다 [27:12].

  • 주요 구성 요소: 추론 능력, 도구, 실행 루프, 기억, 성찰, 내부 하위 목표, 그리고 **가드레일(guardrails)**이 포함된다 [27:35]. 가드레일은 LLM의 출력 공간을 제한하여, 예를 들어 로그를 요청했는데 코드를 작성하는 등 의도치 않은 행동을 방지한다 [27:43].
  • 예시: 사용자가 "결제 실패"를 보고하면, 에이전트는 먼저 대시보드를 확인하여 어떤 서비스가 실패했는지 찾는다(이 과정 자체도 반복적일 수 있다) [30:26]. 적절한 대시보드를 찾으면 해당 서비스의 로그를 조회하고, 로그가 없으면 쿼리 매개변수를 조정하여 다시 시도한다 [30:40]. 최종적으로 Stripe 연결 관련 네트워크 오류를 발견한다 [30:57].
  • 한계:
    • 폭 대 깊이 딜레마: 하나의 에이전트가 모든 분야의 전문가가 되기는 어렵다 (만능 해결사이지만 전문가가 아니다) [31:10].
    • 계획의 취약성: 하위 작업에 몰두하다가 주 목표를 잊어버리는 '계획의 취약성'이 발생할 수 있다 [31:32].
    • 중앙 집중식 병목 현상: 모든 결정이 단일 LLM을 통해 이루어져 전체 프로세스가 LLM API 속도에 병목 될 수 있다 [32:03].
    • 오류 전파: 한 번의 잘못된 추측이 전체 대화 흐름을 망가뜨릴 수 있다 [32:13].
    • 도구 과부하: 복잡한 작업을 위해 수백 개의 도구에 접근해야 할 경우 관리의 어려움이 커진다 [32:27].

5. 다중 에이전트 시스템 (Multi-Agent system)

실제 팀이 전문가들로 구성된 것처럼, 복잡한 실세계 문제를 해결하는 에이전트 시스템도 여러 에이전트로 구성되어야 한다 [32:47]. 이는 단일 에이전트 시스템의 여러 한계를 해결한다.

  • 이점:
    • 특정 전문화: 로그 전담 에이전트, 대시보드 전담 에이전트, 코드 전담 에이전트 등으로 나누어 각 LLM이 더 적은 수의 도구를 다루며 깊은 전문성을 가질 수 있다 [39:11].
    • 긴 작업 및 긴 컨텍스트 관리: 컨텍스트 창이 폭주하는 것을 방지하고, 각 에이전트가 필요한 정보만 집중적으로 처리한다 [39:35].
    • 분산된 의사 결정: 하나의 에이전트가 모든 결정을 내리는 대신, 하위 에이전트들이 각자의 영역에서 의사 결정을 하고 오케스트레이터 에이전트가 이를 조율한다 [39:59].
    • 향상된 오류 방지: 여러 단계의 비평가 루프를 통해 오류가 사용자에게 도달하기 전에 더 많은 보호를 제공한다 [40:17].
    • 도구/컨텍스트 과부하 해결: 각 에이전트가 더 적은 수의 도구를 관리하므로, 전체 시스템의 도구 과부하를 분산한다 [40:48].
  • 설계 패턴:
    • 스캐터-개더(Scatter Gather): 오케스트레이터 에이전트가 여러 하위 작업을 시작하고, 결과를 취합하여 사용자에게 요약한다 (MapReduce와 유사) [43:01].
    • 오케스트레이터 루프(Orchestrator Loops): 오케스트레이터가 일부 에이전트를 호출하고 결과를 받아본 후, 다음으로 호출할 에이전트를 결정하며 반복한다 [43:39].
    • 자유형(Free for all): 에이전트들이 공유된 컨텍스트 내에서 서로를 자유롭게 호출한다 (액터 모델 프로그래밍과 유사) [44:12].
  • 컨텍스트 관리: 각 에이전트가 어느 범위의 컨텍스트를 볼 것인가가 중요하다.
    • 전역 범위(Global Scope): 전체 대화 기록과 내부 에이전트 추적을 모두 본다. 정보 손실이 없지만 컨텍스트 창이 쉽게 폭주한다 [45:10].
    • 자신이 받은 입력만 보는 방식(Own Input): RPC(Remote Procedure Call)처럼 각 에이전트가 자신에게 들어온 요청만 본다. 디버깅이 쉽고 단순하지만, 에이전트가 작업을 잘 수행하는 데 필요한 모든 정보가 요청에 포함되어야 한다 [46:02].
    • 호출 스택 방식(Call Stack): 자신을 호출한 모든 상위 호출을 보지만, 시스템의 다른 부분에서 일어난 일은 보지 않는다 [46:54].
  • 상태 유지(Statefulness): 에이전트가 이전 대화나 작업의 상태를 기억할 것인가의 문제다 [47:18].
    • 완전 상태 유지(Fully stateful): 인간처럼 이전 질문을 기억하고 후속 질문에 답한다. 액터 모델에 더 적합하다 [47:24].
    • 무상태(Stateless): RPC처럼 각 요청이 독립적이어서 이전 요청을 기억하지 않는다. 오케스트레이터 및 워커 유형 작업 흐름에 더 적합하다 [47:43].
  • 비동기 활동: 사용자 경험을 위해 에이전트들이 순차적으로 실행되기보다 병렬로 작업을 수행하고 진행 상황을 업데이트하는 것이 중요하지만, 이는 컨텍스트와 상태 관리 문제를 더욱 복잡하게 만든다 [48:20].

에이전트 시스템의 학습 전략

LLM은 본질적으로 순수 함수적(purely functional) 특성을 가지므로, 동일한 입력에 동일한 출력을 반환한다 [1:03:06]. 이는 에이전트가 과거의 실수를 통해 학습하고 개선하는 데 방해가 된다. 이를 해결하기 위한 두 가지 주요 전략이 있다.

  1. 후속 훈련(Post-training): 모델에 새로운 훈련 데이터를 추가하여 재훈련시키는 고전적인 머신러닝 접근 방식이다 [1:03:46].

    • 장점: 가중치에 지식이 반영되므로 일관성이 높고, 원하는 대로 모델을 조작하여 특정 동작을 가르칠 수 있다.
    • 단점: 모델 재훈련은 인력과 GPU 시간 측면에서 비용이 많이 들고, 한 모델에서 다른 모델로 지식을 이전하기 어렵다. 또한 새로운 지식을 학습시키면서 기존의 지능(시 작성 능력, 지시 따르기 등)을 잊어버리는 문제(망각 현상)가 발생할 수 있다 [1:06:14].

  2. 기억을 통한 학습(Learning through memory): 에이전트가 시스템에 대해 기억해야 할 정보를 외부 스크래치패드나 데이터베이스에 저장해두고, 필요할 때마다 관련 정보를 프롬프트에 삽입하여 활용하는 방식이다 [1:04:01].

    • 장점: 훈련보다 빠르고 유연하며, 모델에 구애받지 않고 적용하기 쉽다.
    • 단점: 기억을 통해 가르칠 수 있는 내용과 양에 한계가 있으며, 모델이 컨텍스트 내의 지시를 따르도록 유도하는 데 한계가 있어 모델의 자연스러운 행동에서 크게 벗어나게 하기 어렵다 [1:06:46].

주요 통찰·논점

복잡성 증가에 따른 에이전트 시스템의 점진적 발전

LLM 기반 에이전트 시스템은 단순한 기능 보조 도구에서 시작하여, 피드백 루프, 외부 도구 통합, 그리고 다수의 특화된 에이전트가 협력하는 복잡한 시스템으로 점진적으로 발전한다. 이 과정은 각 단계에서 이전 단계의 한계를 극복하는 방식으로 진행되며, 최종 목표는 인간 엔지니어의 상위 수준 지시를 자율적으로 처리하는 것이다. 중요한 것은 모든 문제에 최고 수준의 복잡한 시스템이 필요한 것은 아니며, 문제의 본질에 맞는 적절한 복잡성 수준의 에이전트를 구축하는 것이 핵심이다 [17:04].

에이전트 시스템 설계에 적용되는 기존 소프트웨어 공학 원리

강연자들은 에이전트 시스템의 설계 및 아키텍처를 설명하면서 기존 분산 시스템 및 소프트웨어 공학 원리와의 유사성을 강조한다 [38:36]. 에이전트를 함수나 서비스로 비유하고, 다중 에이전트 시스템을 프로그램이나 분산 시스템으로 본다. 이는 단일 에이전트의 복잡성을 분산하고 전문화하는 다중 에이전트 시스템의 필요성을 정당화한다. 모놀리식 코드를 여러 서비스로 나누는 것과 같은 이유로, 단일 에이전트가 너무 복잡해지면 이를 분할하여 성능을 높이고 디버깅을 용이하게 할 수 있다 [41:04]. 컨텍스트 관리, 상태 유지, 비동기 처리와 같은 개념 또한 분산 시스템 설계의 고민과 유사하다 [49:16]. 이는 AI 에이전트 개발이 완전히 새로운 영역이 아니라, 기존 소프트웨어 개발 패러다임의 확장임을 시사한다.

인간의 역할 변화와 에이전트의 한계

AI 에이전트가 발전함에 따라 인간 엔지니어의 역할은 저수준의 반복적인 작업에서 벗어나 고수준의 추상적 사고, 시스템 아키텍처 이해, 목표 설정 및 에이전트 조정으로 전환될 것이다 [1:12:34]. 에이전트는 24시간 내내 작동하며 모든 알림을 처리할 수 있지만, 인간의 확인이 필요한 경우 인간 자체가 병목 현상이 될 수 있다 [1:11:01]. 현재 에이전트의 주요 한계는 추론 능력, 컨텍스트 창의 크기, 긴 작업 처리 능력, 그리고 인간 중심적으로 설계된 도구들이다 [1:09:50]. 특히 에이전트가 자신의 불확실성을 인식하지 못하고 틀린 정보를 확신에 차서 말하는 경향(환각)은 실제 시스템 구축에 큰 도전 과제다 [1:09:15]. 따라서 에이전트에 대한 신뢰를 구축하고 안전하게 사용하기 위한 가드레일(guardrails)은 에이전트 외부의 도구 수준에서 구현되는 경우가 많다 [1:16:28].

인상적인 지점

  • 소프트웨어 엔지니어링의 본질: "어떤 사용자도 기능이 지연된다고 불평하지 않았다. 많은 사용자가 시스템을 사용할 수 없다고 불평했다." [2:20]는 발언은 소프트웨어 엔지니어링에서 신뢰성(reliability)이 새로운 기능 개발보다 우선순위가 높음을 명확히 보여준다. 에이전트가 24시간 내내 시스템을 모니터링하고 문제를 해결하는 능력은 이 관점에서 매우 강력한 이점이다.

  • LLM의 본질적 한계: "LLM이 스스로 자신이 말하는 내용에 얼마나 확신하는지 알 수 있는 방법이 없다" [20:25]는 지적은 현재 LLM의 가장 큰 한계 중 하나를 명확히 짚어준다. 이어 "누군가에게 어려운 질문을 하고 그들의 첫 번째 본능을 맹목적으로 신뢰하는 것과 같다" [20:29]는 비유는 LLM의 이 문제점을 직관적으로 이해시키는 데 효과적이다. 이는 액터-비평가 시스템과 같은 피드백 메커니즘이 왜 필요한지 설명하는 중요한 근거가 된다.

  • 인간 중심 도구의 역설: "LLM에게 주어진 도구의 상당수가 인간을 위해 설계되었기 때문에 LLM에게는 거의 쓸모없는 도구다" [1:10:26]는 언급은 AI 시대에 새로운 도구 설계의 필요성을 강조한다. 기존 도구들이 API가 없거나 처리량이 제한적이며, 인간의 사용 방식에 맞춰져 있어 에이전트의 효율적인 활용을 가로막는다는 점은 인상적인 통찰이다. "이러한 도구를 에이전트를 위해 재구축한다면 어떻게 보일까?" [1:13:07]는 질문은 미래 기술 개발의 방향성을 제시한다.

  • 영어의 새로운 역할과 한계: "영어가 새로운 코드(new code)가 되었다" [1:17:01]는 발언은 LLM의 등장으로 자연어가 프로그래밍 인터페이스로서 중요해진 현상을 압축적으로 보여준다. 그러나 "영어도 이미 병목 현상이다. 코딩할 때 목소리를 사용하는데, 영어를 타이핑하는 것은 너무 느리기 때문이다" [1:17:13]라는 반직관적인 주장은 인간-에이전트 상호작용의 미래가 단순히 자연어를 넘어서 음성이나 에이전트 간의 자체적인 '삑-부-삑-부' 언어로 발전할 수 있음을 상상하게 한다 [1:18:08].
