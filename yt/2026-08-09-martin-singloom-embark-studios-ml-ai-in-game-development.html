TL;DR

이 영상은 8시간이 넘는 컨퍼런스 녹화본이지만, 자막 내용 대부분은 음악, 잡담, 또는 다른 언어로 구성되어 있다. 유일하게 식별 가능한 강연은 엠바크 스튜디오(Embark Studios)의 마틴 싱글룸(Martin Singloom)이 진행한 약 45분간의 머신러닝(ML) 및 인공지능(AI) 게임 개발 사례 발표다 [1:11:03]. 발표자는 게임 개발 과정에서 ML/AI 모델 자체의 우수성만큼이나 조직적 협업과 사용자 중심의 도구 설계가 성공적인 배포에 결정적이라는 점을 개인화 추천 시스템, 퀘스트 분석 도구, 물리 기반 로봇 제어 시스템 사례를 통해 강조한다.

풀시청 판단

이 영상은 8시간 10분 56초 길이의 컨퍼런스 녹화본이지만, 제공된 자막은 영상의 극히 일부(약 45분)만 포함한다. 자막에 명확하게 강연 내용이 기록된 부분은 마틴 싱글룸(Martin Singloom)의 Embark Studios에서의 머신러닝(ML) 구현 사례 발표뿐이다 [1:11:03]. 따라서 이 브리핑은 해당 강연에 한정하여 작성되었다.

마틴 싱글룸의 강연은 게임 개발 분야에서 ML/AI 기술을 도입하고 실제 제품에 적용하는 과정에서 겪는 현실적인 문제와 그 해결책에 대한 깊이 있는 통찰을 제공한다. ML 모델의 기술적 성능뿐 아니라 조직 구조, 팀 간 협업, 사용자 경험에 대한 고려가 얼마나 중요한지 여러 사례를 통해 설득력 있게 설명한다.

이 강연을 풀시청할 가치가 있는 사람:

  • 게임 개발자 및 ML 엔지니어: 게임 산업에서 ML/AI를 실제 프로젝트에 적용하는 구체적인 사례와 기술적/조직적 난관에 대한 현실적인 경험을 얻을 수 있다.
  • ML/AI 제품 관리자 및 리더: ML 모델 배포의 성공을 좌우하는 비기술적 요소(조직 문화, 사용자 통합)의 중요성을 이해하는 데 도움이 된다.
  • 창의 산업 종사자: 예술가, 디자이너 등 창의적 인력과 ML 기술 간의 효과적인 협업 방식에 관심 있는 사람에게 유용하다.

강연의 약점 또는 한계:

  • 영상 전체가 아닌 한 강연자의 발표 내용에 국한된다.
  • 기술적인 세부 구현보다는 개념적 설명과 실제 문제 해결 과정에 초점을 맞추므로, 특정 ML 모델의 심층적인 기술적 내용은 다루지 않는다.
  • 발표 시점에 따라 최신 기술 동향이 일부 반영되지 않을 수 있다.

핵심 내용

엠바크 스튜디오와 ML/AI의 역할

엠바크 스튜디오는 AAA 비디오 게임 제작이 너무 어렵다는 문제의식에서 출발했다 [1:12:51]. 수천 명의 인력과 수년의 시간이 필요하며, 이로 인해 창의적인 위험을 감수하기 어렵다는 점을 해결하고자 했다. 새로운 기술을 활용하여 더 빠르고, 더 재미있게 게임을 만들고, 더 과감한 시도를 하는 것이 스튜디오의 핵심 이념이다 [1:13:14].

이러한 새로운 기술에는 사진측량(photogrammetry)이나 비파괴적인 캐릭터 아트 파이프라인 등이 포함되지만, ML/AI는 특히 두 가지 방식으로 게임 개발에 기여한다 [1:14:12]. 첫째, 기존 작업을 더 빠르게 수행하도록 돕는다. 코딩 에이전트(예: Claude)를 사용해 코드 작성 속도를 높이거나, 그림자 제거 모델을 사용해 Dlight 텍스처를 빠르게 만드는 식이다 [1:14:23]. 둘째, 기존에는 불가능했던 새로운 일들을 가능하게 한다 [1:14:53]. Arc Raiders의 로봇, 퀘스트 시스템, 게임 내 개인화 기능 등이 여기에 해당한다 [1:15:02]. 발표자의 팀은 주로 ML/AI를 활용하여 이전에 불가능했던 '새로운 일'을 만드는 데 집중하고 있다 [1:15:38].

추천 시스템: 알고리즘보다 중요한 조직 문제 [The Finals]

The Finals는 무료 플레이 게임이므로 게임 내 상점이 매우 중요하다 [1:16:24]. 2년 동안 4,000개가 넘는 꾸미기 아이템이 출시되었지만, 상점 화면이 작아 오래된 아이템들이 플레이어에게 노출되기 어렵다는 문제가 있었다 [1:16:41]. 개발팀은 아마존이나 넷플릭스처럼 개인화된 추천 모델을 통해 이 문제를 해결하고자 했다 [1:17:27].

여러 추천 모델을 테스트한 결과, '쉽게 얕은 오토인코더(EASE, embarrassingly shallow autoencoders)' 모델이 회수율(recall)과 평균 상호 순위(mean reciprocal rank) 모두에서 가장 뛰어난 성능을 보였다 [1:17:00]. 이 모델은 파이썬 코드 네 줄로 학습이 가능할 정도로 매우 간단하다 [1:18:38]. 이 모델을 상점의 '추천(for you)' 섹션에 적용하여 AB 테스트를 진행한 결과, 구매자 수가 400% 증가하고 게임 내 화폐 및 실제 화폐 지출이 크게 늘어나는 엄청난 성공을 거두었다 [1:19:42].

그러나 이 프로젝트는 배포 과정에서 심각한 난관에 부딪혔다. ML 팀이 다른 부서와 고립되어 있어 프로젝트에 대한 이해와 지지를 얻기 어려웠고 [1:20:10], AB 테스트 승인도 쉽지 않았다. 심지어 초기 AB 테스트 분석에서는 유의미한 결과가 없다는 잘못된 보고가 나오기도 했다 [1:21:10]. 이 모든 문제는 ML 팀이 다른 팀과 소통하고 협업하는 방식의 부재에서 비롯되었다 [1:21:50]. 해결책은 간단했다. ML 엔지니어를 실시간 운영팀(live ops team) 사무실로 물리적으로 이동시켰다 [1:22:00]. 그러자 일상적인 소통을 통해 모든 의사소통 문제가 사라지고, 테스트 및 분석 목표가 명확해지면서 프로젝트가 순조롭게 진행되었다 [1:22:09]. 여기서 얻은 교훈은 알고리즘이 아무리 단순하고 우아하더라도 배포되지 않으면 소용없으며, 때로는 '자리 배치'와 같은 사소한 조직적 변화가 전체 작업을 해결할 수 있다는 것이다 [1:22:34].

LLM 기반 퀘스트 분석: 사용자의 작업 방식에 맞춰야 성공한다 [Arc Raiders]

Arc Raiders와 같은 게임의 퀘스트는 일반적인 책이나 영화의 선형적인 서사와 달리 그래프 형태로 연결되는 비선형적인 구조를 가진다 [1:24:37]. 플레이어가 퀘스트를 수행하는 순서에 따라 이야기에 대한 인식이 달라지므로, 모든 가능한 경로를 QA(품질 보증)하는 것은 매우 어렵고 지루한 작업이다 [1:26:09].

이러한 문제를 해결하기 위해 개발팀은 거대 언어 모델(LLM)을 분석 도구로 활용하는 아이디어를 떠올렸다 [1:27:11]. LLM은 피로를 모르고, API를 호출할 때마다 새로운 관점에서 이야기를 읽을 수 있으므로, 퀘스트의 다양한 플레이 경로를 시뮬레이션하고 내러티브의 모순이나 불일치를 찾아내는 데 적합했다 [1:27:16]. 초기 프로토타입은 Notion에 저장된 퀘스트 정보를 가져와 LLM 기반 워크스루(walkthrough)를 수행하는 웹 도구였고, 이를 통해 여러 불일치를 발견하며 성공적인 결과를 보여주었다 [1:29:09].

그러나 게임 출시가 임박하여 퀘스트 구조가 더 복잡해지자 내러티브 팀은 이 도구 사용을 중단했다 [1:29:37]. 이유는 Notion이 텍스트 기반이라 퀘스트 간 연결을 시각적으로 '화살표로 그릴' 수 없었기 때문이다 [1:30:04]. 내러티브 팀은 Miro 같은 화이트보드 소프트웨어에서 퀘스트 간 관계를 시각적으로 파악하는 데 더 큰 가치를 두었다 [1:30:46]. 이는 LLM의 고급 기능보다 사용자의 기본적인 작업 방식에 맞는 시각적 도구가 더 중요했음을 보여준다.

이 문제를 해결하기 위해 개발팀은 Spindle이라는 새 도구를 만들었다 [1:31:03]. Spindle은 기존 LLM 분석 기능과 더불어 사용자가 퀘스트 간 화살표를 시각적으로 그릴 수 있는 기능을 제공했다 [1:31:13]. 이 기능이 추가되자 내러티브 팀은 다시 도구를 사용하기 시작했고, LLM 기반의 내러티브 지원 기능도 함께 활용할 수 있게 되었다 [1:31:31]. 핵심 교훈은 ML 도구도 다른 모든 도구와 마찬가지로 사용자가 있는 곳에서 사용자의 필요를 충족시켜야 성공한다는 점이다 [1:30:46].

물리 기반 로봇 제어: 복잡성 극복을 위한 고전 AI와 예술가 협업 [Arc Raiders]

Embark Studios는 Arc Raiders에서 재플레이 가능성(replayability)과 동적 변화(emergence)를 높이기 위해 거대한 물리 기반 로봇을 구현하고자 했다 [1:34:10]. 물리학 시뮬레이션을 통해 매 세션마다 예측 불가능하고 고유한 상황이 발생하도록 하는 것이 목표였다 [1:34:47].

로봇 제어에는 강화 학습(Reinforcement Learning, RL)이 사용되었다 [1:35:46]. RL은 신경망으로 구성된 정책(policy)이 행동을 결정하고, 로봇이 그 행동에 대한 환경의 관찰 결과와 보상(reward)을 받아 정책을 수정하는 방식으로 작동한다 [1:35:55]. 초기 Unity 데모에서는 목표 플레이어에게 가까워지고, 똑바로 서 있으며, 플레이어를 바라보는 것을 보상으로 설정하여 유기적인 움직임(예: 급회전 시 자연스럽게 엉덩이를 내리는 움직임)을 구현할 수 있었다 [1:38:36].

초기 Arc Raiders 버전에 로봇을 적용했을 때는 재미있고 동적인 움직임을 보였지만, 로봇의 걸음걸이가 "흔들리고 불안정(floaty and wobbly)"하게 느껴져 애니메이션 관점에서는 만족스럽지 않았다 [1:39:35]. 개발팀은 관절의 강성, 감쇠, 보상의 가중치(이동, 직립, 방향, 에너지 사용 등)를 수년간 미세 조정하여 개선을 시도했다 [1:40:26]. 그러나 여러 행동(예: 걷기와 멈추기)을 하나의 모델에 학습시키자 '행동 오염(behavior bleed)' 문제가 발생했다. 로봇이 언제든 멈추라는 명령을 받을까 봐 "겁먹은(scared)" 듯이 천천히 걷게 되는 것이다 [1:42:42].

이 문제를 해결하기 위해 고전 게임 AI 기법인 **행동 트리(Behavior Trees)**를 도입했다 [1:43:16]. 개발팀은 '항상 걷는' 모델과 '멈추는' 모델을 각각 훈련하고, 행동 트리가 상황에 따라 이 두 모델 중 하나를 선택하도록 했다 [1:43:24]. 이 방식은 ML 엔지니어링과 게임 디자인을 분리하고, 새로운 행동을 마치 레고 조각처럼 쉽게 추가할 수 있게 했다 [1:44:31].

하지만 로봇이 "날렵하게, 점프하듯이, 무겁게" 움직이도록 하는 등 구체적인 움직임 스타일을 제어하는 것은 여전히 어려웠다. 복잡한 움직임에 대한 보상 함수를 설계하는 것은 매우 복잡하고 확장성이 떨어졌다 [1:46:51]. 이때 **적대적 움직임 사전(AMP, Adversarial Motion Prior)**이라는 새로운 기술을 도입했다 [1:47:34]. 애니메이터가 만든 걷기 애니메이션을 RL의 보상으로 활용하여, 로봇이 애니메이터의 의도대로 움직이도록 학습시켰다 [1:48:28]. 이를 통해 예술가가 로봇의 움직임을 직접 제어할 수 있게 되었고, 스타일 변경도 훨씬 쉬워졌다 [1:48:47].

마지막으로 로봇의 시각 시스템에도 문제가 있었다 [1:50:01]. 기존의 그리드 기반 레이캐스팅 방식은 로봇 위에 가상의 격자를 만들고 각 격자점에서 아래로 레이를 쏴 지면의 높이 지도를 생성했다 [1:51:06]. 이 방식은 오버행 구조(터널, 다리) 아래에서는 지형을 인식하지 못하고, 벽을 투시하는 문제도 있었다 [1:51:44]. 해결책은 포인트 클라우드(point clouds) 시스템이었다 [1:52:10]. 로봇 자체에서 레이를 발사하여 주변 환경의 점 구름을 생성하고, 이를 통해 터널과 같은 복잡한 지형도 정확하게 인식할 수 있게 되었다 [1:52:18].

이러한 모든 경험을 통해 개발팀은 알고리즘과 모델도 중요하지만, 조직, 도구, 그리고 예술가/디자이너와 같은 사용자의 작업 방식과 파이프라인을 이해하는 것이 ML 모델을 실제 제품에 적용하는 데 핵심적이라는 교훈을 얻었다 [1:54:10].

주요 통찰·논점

ML 모델 배포의 핵심은 조직 문화와 협업

아무리 혁신적이고 효율적인 ML 알고리즘을 개발하더라도, 그것이 실제 제품이나 서비스에 배포되어 사용자에게 가치를 전달하지 못하면 무용지물이다 [1:22:26]. Embark Studios의 추천 시스템 사례는 ML 팀이 다른 부서(상업팀, 실시간 운영팀)와 고립되었을 때 발생하는 의사소통, 이해관계 조정, AB 테스트 승인, 심지어 결과 분석에서의 오류와 같은 비기술적 병목 현상을 명확히 보여준다. 이러한 문제를 해결하기 위한 'ML 엔지니어의 물리적 자리 이동'이라는 간단한 조직 변화는 기술 자체의 복잡성과는 무관하게 ML 배포 성공의 결정적인 요소가 될 수 있음을 시사한다 [1:22:00]. 이는 ML 모델을 개발하는 것만큼이나 이를 사용하는 팀과의 협업 환경을 구축하는 것이 중요하다는 점을 강조한다.

사용자 중심의 도구 설계가 ML 도입의 성패를 가른다

최첨단 ML 기술을 활용한 도구라도 사용자의 실제 작업 방식과 선호를 무시하면 채택되지 않는다. LLM 기반 퀘스트 분석 도구 사례는 이 점을 극명하게 보여준다. 강력한 분석 기능을 제공했음에도 불구하고, 내러티브 디자이너들이 퀘스트 간 관계를 '화살표로 시각적으로 표현'하려는 기본적인 요구사항을 충족시키지 못했기 때문에 사용이 중단되었다 [1:30:30]. 이 사례는 ML 도구를 개발할 때 기술적 성능에만 집중할 것이 아니라, 목표 사용자의 기존 워크플로, 직관적인 인터페이스, 그리고 사용자가 도구를 통해 달성하고자 하는 '가장 기본적인 니즈'를 깊이 이해하고 충족시켜야 한다는 점을 시사한다. 도구는 사용자가 있는 곳으로 가서 그들의 필요를 해결해야 성공할 수 있다 [1:30:46].

게임 AI 개발에서 고전 AI 기법과 ML의 시너지

물리 기반 로봇 제어 사례는 최신 ML 기법(강화 학습)과 고전 게임 AI 기법(행동 트리)이 상호 보완적으로 작용하여 더 나은 결과를 만들어낼 수 있음을 보여준다. 강화 학습은 로봇의 유기적이고 동적인 움직임을 생성하는 데 탁월하지만, 여러 복잡한 행동을 하나의 모델로 제어할 때 발생하는 '행동 오염' 문제에 취약하다 [1:42:42]. 이때 행동 트리를 도입하여 각 행동에 특화된 ML 모델들을 효과적으로 전환하고 조합함으로써, 각 모델의 순수한 성능을 유지하면서도 복잡한 행동 제어의 유연성을 확보할 수 있었다 [1:43:16]. 또한 애니메이터의 작업물을 ML 모델 학습의 '보상'으로 활용하는 적대적 움직임 사전(AMP)은 ML과 예술 분야의 협업을 통해 창의적 의도를 기술적으로 구현하는 효과적인 방법을 제시한다 [1:48:28]. 이는 각 기술의 강점을 파악하고 적절히 통합하는 것이 복잡한 문제 해결의 핵심임을 보여준다.

인상적인 지점

  • "엉덩이 움직임"의 탄생 [1:38:36]: 로봇이 급회전할 때 자연스럽게 엉덩이를 살짝 내리는 움직임을 보였는데, 이는 개발팀이 의도적으로 설계한 것이 아니라 보상 함수와 물리학 시뮬레이션의 결과로 자연스럽게 발생한 현상이다. ML이 예상치 못한 유기적인 결과를 만들어내는 재미있는 예시다.

  • "겁먹은 로봇" [1:42:42]: 로봇에게 걷기와 멈추기라는 두 가지 행동을 하나의 ML 모델로 학습시키자, 로봇이 언제든 멈추라는 명령을 받을까 봐 '겁먹은' 듯이 움직이는 현상이 나타났다. 이는 ML 모델이 복잡한 다중 행동을 학습할 때 발생하는 '행동 오염' 문제를 매우 직관적이고 인상적으로 보여주는 비유다.

  • "화살표를 그려야 하는 디자이너" [1:30:30]: LLM 기반의 강력한 퀘스트 분석 도구가 개발되었지만, 내러티브 팀은 텍스트 기반 Notion 대신 화살표를 시각적으로 그릴 수 있는 Miro를 선호하여 도구 사용을 중단했다. 이는 아무리 고도의 기술이라도 사용자의 가장 기본적인 작업 방식과 직관적인 필요를 충족시키지 못하면 외면받을 수 있다는 점을 상기시킨다.
